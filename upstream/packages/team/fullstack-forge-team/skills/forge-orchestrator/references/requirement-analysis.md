# 需求分析方法论（requirement-analysis）

> 适用角色：选品洞察师（product-scout）
> 用途：把用户模糊的想法转化为"做什么系统、给谁用、值不值得做"的清晰判断。平台选型请配合阅读 `platform-selection.md`。

---

## 一、需求梳理方法

### 1.1 从一句话到结构化需求

用户的需求通常是一句话，例如"我想做个帮宠物主人约洗宠的 App"。需求梳理就是把这句话拆成五个要素：

| 要素 | 追问 | 示例回答 |
|------|------|----------|
| 业务目标 | 做成之后想得到什么？ | 线上接单、提高门店利用率 |
| 目标用户 | 谁在用？分几类角色？ | 宠物主人（C端）、门店/美容师（B端） |
| 核心场景 | 什么时间、什么状态下用？ | 主人在家提前预约周末洗护 |
| 关键流程 | 从哪里进、做什么、得到什么？ | 选门店→选服务→选时间→下单支付→到店核销 |
| 约束条件 | 预算、时间、人力、合规限制？ | 预算5万内、3个月上线、个人开发者 |

**输出标准**：五要素中任何一项回答不了，列入"待确认问题清单"向用户提问，禁止脑补后直接往下做。

### 1.2 用户故事模板

所有功能需求统一用用户故事表达，保证可验证：

```
作为 <角色>，
我想 <在什么场景下做什么事>，
以便 <得到什么价值>。
验收：<可测量的完成标准>
```

示例：

- 作为宠物主人，我想在周末前 3 天预约门店洗护并在线支付，以便到店不用排队。
  验收：可按门店营业时间选择时段；支付成功后收到带核销码的预约确认；取消预约在开始前 2 小时内免手续费。

写用户故事的三条纪律：
1. 一个故事只描述一件事，出现"并且/同时"就拆分；
2. 验收标准必须可测量（可点、可见、可统计），"体验流畅"不是验收标准；
3. 故事必须落在某个角色上，"用户"过于笼统时要先拆角色（浏览者/下单者/管理后台运营者……）。

### 1.3 需求分类：KANO 简化版

不需要完整 KANO 问卷，用简化四分法对需求归类，直接服务于后续 MVP 取舍：

| 类别 | 判断标准 | 处理方式 |
|------|----------|----------|
| 基本型（必备） | 没有它用户直接流失/无法使用 | MVP 必须包含 |
| 期望型（越多越好） | 有的话满意度明显提升 | MVP 尽量包含，不足时进 V1.1 |
| 兴奋型（惊喜） | 用户没想到但会惊喜 | V1.1/V2.0，MVP 不做 |
| 无差异/反向 | 做不做无所谓甚至反感 | 砍掉，记录原因 |

快速判定口诀：**砍掉它，产品还成立吗？** 不成立 → 基本型；满意度大降 → 期望型；没感觉 → 兴奋型或无差异。

### 1.4 需求池记录格式

对收集到的每条需求编号入池，方便后续追溯与变更管理：

```
REQ-001 | 类型：基本型 | 角色：宠物主人 | 故事：... | 优先级建议：P0 | 状态：已确认
```

## 二、MVP 定义原则

### 2.1 MVP 的定义

MVP（最小可行产品）= **能完整跑通核心价值闭环的最小功能集**。判断标准不是"功能少"，而是：

1. 用户能从进入 → 完成核心动作 → 得到价值，全流程无断点；
2. 运营方能完成最基本的供给侧管理（有 B 端的系统必须含最小后台）；
3. 数据能被记录，为下一轮迭代提供依据。

### 2.2 MVP 取舍四原则

1. **闭环优先**：先保证"一个角色从头到尾把核心事情办成"，再扩展多角色、多场景。
2. **单端先行**：除非业务强依赖双端（如骑手端+用户端缺一不可），否则只做一个端。
3. **人工替代**：MVP 阶段能用人工/Excel/微信群顶住的后台能力（如客服、对账、内容审核），先用人工，把开发量留给核心闭环。
4. **第三方优先**：支付、短信、地图、推送、统计等通用能力直接接第三方服务，不自研。

### 2.3 MVP 反面清单（出现即回调范围）

- MVP 功能清单超过 15 个功能点（大概率把 V1.1 的内容塞进来了）；
- 包含"锦上添花"类功能：积分商城、复杂权限体系、多语言、深色模式、推荐算法；
- 为"未来可能"预留的模块（真正的扩展靠架构预留，不靠提前开发）。

## 三、可行性评估四维度

对"值不值得做、能不能做成"给出结构化评估，每个维度给结论 + 依据 + 风险等级（低/中/高）：

### 3.1 技术可行性

- 核心能力是否全部有成熟方案/第三方服务可承接（支付、音视频、地图、IM、OCR 等）？
- 是否依赖未验证的自研技术？依赖越多风险越高；
- 团队/用户的技术栈是否能覆盖所选方案（结合平台选型结论）；
- 结论表述示例：技术可行（低风险）：核心功能全部可用成熟组件拼装，无自研攻关点。

### 3.2 成本可行性

按三项估算并给出区间（不要给假精确的单点数字）：

| 成本项 | 估算方法 |
|--------|----------|
| 开发成本 | 人日 × 功能点数（可按"页面数×2~4人日/页 + 后端接口"粗估） |
| 运行成本 | 云服务器/数据库/CDN/短信/证书 月度费用区间 |
| 隐性成本 | 软著申请、证书年费（苹果开发者 $99/年 等）、类目资质办理、备案时间 |

**红线**：估算总成本超出用户预算上限且无压缩空间时，必须在报告中明确标红，并给出降配方案（砍端、砍功能、换低成本技术路线）。

### 3.3 时间可行性

- 拆出阶段里程碑（需求确认→设计→开发→测试→上架→上线），各阶段给时间区间；
- 特别注意**上架审核周期**必须计入：App Store 首审常见 1~7 天（可能被拒重来）、微信小程序审核 1~7 天、软件著作权如需用于上架资质需要更早启动；
- ICP 备案（大陆服务器建站/小程序）通常 1~3 周，属于最容易拖垮上线时间的前置项，必须提前列出。

### 3.4 合规可行性

逐项核对，涉及即提示：

- **ICP 备案/许可**：大陆服务器网站、小程序均需 ICP 备案；经营性网站可能需 ICP 许可证；
- **应用商店类目资质**：社交（含聊天）需证明材料、直播需网络文化经营许可、医疗健康需对应资质、金融类基本禁入或强资质；
- **个人信息保护**：隐私政策、收集最小化、未成年人保护条款；涉及人脸/身份证 OCR 需单独合规评估；
- **支付**：微信/支付宝支付需商户号，个体户/公司主体限制；
- **内容安全**：UGC（用户发布内容）需审核机制与举报通道，否则商店审核风险高。

**一票否决项**：法律法规明确禁止的用途（赌博、诈骗、色情等）直接终止，不做方案。

## 四、需求确认清单

输出报告前逐项核对，未确认项在报告中单列"待用户确认"章节：

- [ ] 业务目标一句话确认（用户认可的表述）
- [ ] 目标用户与角色划分确认
- [ ] 核心使用场景确认（至少 1 个主场景走通）
- [ ] 预算上限（开发 + 年度运行）确认
- [ ] 期望上线时间确认
- [ ] 平台/端倾向确认（用户自己的偏好也要记录）
- [ ] 是否已有品牌名、域名、主体资质（个体户/公司）、已备案域名
- [ ] 是否需要后台管理（多数"小工具"类需求用户想不到后台）
- [ ] 合规项核对完成（备案/类目资质/隐私）
- [ ] 用户对 MVP 范围的认可（或明确列出分歧点）

## 五、常见需求陷阱

1. **把方案当需求**：用户说"我要个小程序"，实际要问清楚他要用它达成什么；直接按字面执行会做出错误形态的产品。
2. **只听发起人，不看使用者**：发起人（老板）与实际用户（员工/顾客）需求经常冲突，报告必须区分"发起人诉求"与"使用者诉求"。
3. **隐性依赖被忽略**：内容展示类需求忽略 CMS 后台、电商忽略售后流程、预约类忽略取消/改期规则——这些往往是基本型需求。
4. **把竞品当需求**：用户拿着竞品截图说"照这个做"，要提炼竞品背后的用户场景，而不是逐像素复刻；复刻常带入与本项目无关的复杂度。
5. **范围蠕变**：确认过程中用户不断"顺便加一个"，必须维护需求池并把新增项标注对成本/工期的影响，让用户在知情下取舍。
6. **悲观沉默**：发现需求不可行或严重超预算时，必须明确说"不建议做/需调整"，禁止含糊带过让问题留到开发阶段爆发。

## 六、需求访谈提问清单

首轮沟通按此清单提问，避免漏项（按需取舍，一次最多问 8~10 个，分轮进行）：

### 业务与目标
1. 用一句话说，这个产品做成后最理想的状态是什么？
2. 现在没有它的时候，这件事怎么解决的？痛点在哪？
3. 怎么判断产品做成功了？（期望看到的第一个数字）

### 用户与场景
4. 谁是第一优先级用户？（只能选一个主人群）
5. 用户在什么情况下会打开它？一天/一周用几次？
6. 用户现在用什么替代品（竞品/Excel/微信群/纸质登记）？最不满意它什么？

### 范围与约束
7. 首版如果只能做一件事，是哪件事？
8. 预算范围？期望上线时间？上线后谁来维护（有技术人吗）？
9. 有没有已有的域名、主体资质（个体户/公司）、商标、品牌素材？
10. 有没有"必须有"的硬性要求（合规、老板指定、渠道约定）？

**提问纪律**：不诱导（不问"你要不要 XX 功能"，问"你想怎么解决 XX 问题"）；追落地（每个理想化描述都追问"第一版最小怎么算"）。

## 七、需求排序与依赖标注

需求池确认后，按"价值 × 成本"两维排序，输出 MVP 选取依据：

| 需求 | 价值（高/中/低） | 成本（高/中/低） | 依赖 | 进 MVP |
|------|------------------|------------------|------|--------|
| 在线支付 | 高 | 中 | 需先完成商户号申请（约1周） | 是 |
| 预约时段管理 | 高 | 低 | 无 | 是 |
| 积分商城 | 低 | 高 | 无 | 否（V1.2） |

排序规则：
1. 高价值低成本 → 先做；高价值高成本 → 拆小再做；低价值 → 不做并记录原因；
2. 标注**技术依赖**（如"推送依赖 App 端"）与**业务依赖**（如"到店核销依赖先有门店入驻"），被依赖项优先级自动提升；
3. MVP 选取结果回写需求池状态，与用户确认后**冻结**——冻结后再新增的需求一律走变更管理（见 product-design.md）。

## 八、报告输出结构（选品洞察师适用）

最终[需求与平台选型报告]按以下结构组织（平台部分配合 platform-selection.md 的选型结论）：

1. **需求概述**：业务目标 / 目标用户 / 核心场景 / 约束（用户确认后的表述）
2. **核心需求清单**：KANO 分类 + 用户故事 + 优先级建议
3. **可行性评估**：技术 / 成本（区间估算） / 时间（含备案与审核周期） / 合规（逐项核对结论）
4. **待确认问题清单**：未决项 + 每项对方案的影响说明
5. **结论与建议**：值不值得做 + MVP 范围建议 + 交给平台选型的输入项
