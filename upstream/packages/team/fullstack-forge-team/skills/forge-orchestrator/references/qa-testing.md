# 测试保障体系（qa-testing）

> 适用角色：质量测试官（qa-tester）
> 用途：为多端产品制定测试策略、设计用例、设定质量门禁。上游输入：PRD（含验收标准）、技术研发方案。

---

## 一、测试策略（四层）

| 层次 | 测试内容 | 重点 |
|------|----------|------|
| 功能测试 | 按 PRD 验收标准逐项验证业务流程 | 正常流 + 异常流，覆盖所有 P0 功能 |
| 兼容测试 | 多端、多机型、多系统版本 | 用下文矩阵选择覆盖范围 |
| 性能测试 | 响应时间、并发、资源占用、弱网 | 核心接口与首屏，按性能预算验收 |
| 安全测试 | 越权访问、注入、敏感信息泄露、支付篡改 | P0 级：登录鉴权、支付接口、个人信息 |

### 测试节奏（分级发布）

1. **冒烟测试**：提测准入——核心流程能跑通才接测，跑不通直接打回；
2. **全量功能测试**：P0 用例 100% 执行，P1 用例按风险抽查；
3. **回归测试**：修复后回归 + 上线前回归（维护核心回归集）；
4. **验收测试（UAT）**：按 PRD 验收标准由产品/用户确认。

---

## 二、多端多机型用例设计矩阵

按产品形态选择对应矩阵，**目标机型 = 目标用户的真实设备构成**（引用选型报告）：

### 网站
- 浏览器：Chrome / Edge / Safari 各最新两个大版本 + 微信内置浏览器；
- 分辨率：1920×1080、1440×900、移动端 375×667 / 390×844、平板；
- 专项：首屏加载（4G 模拟）、响应式断点、表单在 iOS 键盘下的表现。

### App（iOS / Android / 鸿蒙）
- iOS：最新版 + 前两代系统版本 × 小屏（SE 尺寸）/ 标准屏 / 大屏（Max）至少 3 台代表机型；
- Android：主流厂商（华为/小米/OPPO/vivo）各 1 代表机型 + 性能机 1 台，覆盖国内定制系统的权限/推送差异；
- 鸿蒙：HarmonyOS 最新版 1~2 台，验证 ArkTS 页面与多设备自适应；
- 专项：弱网/断网恢复、后台切前台、来电中断、耗电发热、安装升级（覆盖安装/卸载重装）。

### 小程序
- 基础库：最新稳定版 + 最低支持版本；
- 机型：iOS 微信 + Android 微信 + 开发者工具三端核对（渲染层差异大）；
- 专项：分包加载、支付流程、订阅消息授权拒绝后的降级、分享卡片链路。

## 三、用例编写模板

每条用例包含以下字段，异常流用例必须与正常流分开编号：

```
用例编号：TC-LOGIN-001
模块：登录
标题：手机号+验证码正常登录
优先级：P0
前置条件：已注册手机号 138****0001；验证码服务正常
步骤：
  1. 打开登录页，输入已注册手机号
  2. 点击"获取验证码"
  3. 输入 6 位正确验证码
  4. 点击"登录"
预期结果：
  1. 步骤2后 60 秒内收到验证码，按钮进入 60s 倒计时
  2. 步骤4后 3 秒内跳转首页，右上角显示用户昵称
```

异常流示例（与上同模板）：
- 验证码错误/过期 → 明确报错文案，不泄露"该号是否注册"；
- 获取验证码频率超限（60s 内重复点击）→ 按钮禁用 + 提示；
- 断网状态点登录 → 友好提示 + 重试按钮，不白屏不崩溃。

**用例设计方法**：等价类划分（合法/非法输入分区）、边界值（0/1/最大值/最大+1）、场景法（完整业务链路）、状态迁移（订单状态机逐跳验证）。

## 四、Bug 报告规范

每条 bug 必须包含，缺项视为无效报告：

| 字段 | 要求 |
|------|------|
| 标题 | 一句话可定位：`[模块] 现象 + 条件` |
| 严重级别 | P0 致命（崩溃/资金错误/数据丢失/主流程阻断）、P1 严重（主要功能错误、严重体验问题）、P2 一般（次要功能异常）、P3 轻微（文案/样式） |
| 环境 | 设备型号、系统版本、App/基础库版本、账号、网络状态 |
| 复现步骤 | 编号步骤，他人按步骤必须能复现 |
| 实际结果 vs 预期结果 | 两者分开写 |
| 证据 | 截图 / 录屏 / 日志 / 请求响应 |
| 复现概率 | 必现 / 高频 / 偶现（注明次数比例） |

流程约定：新 bug → 确认（可复现/有效）→ 修复 → 回归验证 → 关闭；偶现 bug 附日志并跟踪至概率归零。

---

## 五、质量门禁标准

上线前必须全部满足，任一不满足不得放行：

1. **P0 bug = 0**（存在即禁止上线）；
2. P1 bug 全部修复或有用户已知情的书面豁免（附规避方案）；
3. **核心链路用例通过率 100%**（登录、下单/支付、核心业务闭环）；
4. 全量用例执行率 100%，通过率 ≥95%；
5. 性能达标：核心接口 P95 响应 ≤ 目标值、App 崩溃率 ≤0.1%（千分之一下同）、首屏达标；
6. 兼容矩阵执行完成，无阻塞级适配问题；
7. 安全测试通过：无高危漏洞（越权、注入、明文敏感信息）；
8. 合规项验证：隐私政策可访问、权限申请文案正确、备案/资质生效。

## 六、验收测试清单（上线前逐项核对）

- [ ] PRD 全部 P0 功能验收通过（逐条对照验收标准）
- [ ] 全部核心用户流程端到端走通（含异常分支）
- [ ] 支付全流程真实支付 1 笔 + 全额退款 1 笔验证
- [ ] 推送/消息触达真实设备收到并跳转正确
- [ ] 新用户从零注册走完全流程（未登录→登录→核心动作）
- [ ] 多端矩阵内机型抽查无阻塞问题
- [ ] 弱网/断网/后台恢复无崩溃、无数据错乱
- [ ] 数据埋点事件全部上报正确（对应北极星指标口径）
- [ ] 提测 bug 全部关闭或书面豁免
- [ ] 回归测试集执行通过

## 七、自动化测试策略

MVP 阶段自动化以"投入产出比"为纲，不盲目追求覆盖率：

| 层 | 自动化内容 | 优先级 |
|----|------------|--------|
| 接口层 | 核心接口冒烟集（登录/下单/支付回调） | P0，上线前必须具备 |
| 单元层 | 核心业务规则（金额计算、状态机流转） | P1 |
| UI 层 | 单端核心链路（App 用 Appium / 小程序用 miniprogram-automator） | P2，版本稳定后再投入 |

执行约定：
1. 自动化用例与手工用例同源（同一用例库标注"可自动化"），避免两套口径；
2. 自动化接入 CI：每次构建跑接口冒烟，失败即阻断发布流程；
3. 回归集 = 自动化冒烟 + 手工核心链路，总时长控制在 30 分钟内，保证回归可频繁执行。

## 八、性能测试细化

按技术方案的非功能性基线执行，逐项给实测值：

1. **接口性能**：核心接口压测（JMeter/wrk），记录 P50/P95/P99 与错误率曲线，找出性能拐点并发数；
2. **前端性能**：首屏 FCP/LCP（Lighthouse + 真实机型复核），核查图片资源体积与压缩；
3. **App 专项**：冷启动时长（≤3s）、内存峰值、弱网降级表现、耗电发热（30 分钟基准测试）；
4. **小程序专项**：主包体积（≤2MB）、分包加载耗时、setData 单次数据量核查；
5. **数据造数**：预置真实量级数据（万级列表、千级账号）再压测——空库测出的性能是假象。

输出《性能测试报告》：目标值 vs 实测值 vs 结论；未达标项列为发布阻塞项并同步团长。

---

## 九、安全测试清单

MVP 必测项（可借助工具，但结论必须逐条落到清单）：

- [ ] 水平越权：A 用户 token 访问 B 用户资源（订单/地址/消息）被拒绝
- [ ] 垂直越权：普通用户调用管理接口被拒绝
- [ ] SQL 注入：关键输入点参数化验证（常用 payload 抽测）
- [ ] XSS：昵称/评论/富文本等输入点脚本过滤
- [ ] 敏感信息：接口响应与页面不回显密码明文、身份证全文、完整手机号（脱敏）
- [ ] 接口防刷：短信/登录/下单频率限制生效
- [ ] 支付安全：金额服务端校验（篡改请求不生效）、回调验签、重复回调幂等
- [ ] 传输：全站 HTTPS、证书链完整有效

高危项（越权、支付篡改、敏感信息明文）任一不通过即为发布阻塞。

## 十、测试报告模板

```
测试报告 | {版本号} | {日期}
一、结论：是否达到质量门禁（逐项对照门禁标准给出 是/否）
二、测试范围：执行用例数 / 通过率 / 覆盖模块清单
三、缺陷统计：P0 x 个（全部关闭）、P1 x 个（状态）、P2/P3 存量与豁免说明
四、兼容执行：矩阵覆盖情况与遗留问题
五、性能与安全：关键数据与结论
六、遗留风险：已知问题 + 影响评估 + 规避建议
```

## 十一、测试排期参考

以 4 周开发周期为例：
- 第 3 周：用例评审完成 → 提测冒烟 → 全量功能测试（按模块提测节奏滚动执行）；
- 第 4 周上半：回归测试 + 兼容矩阵执行 + 性能/安全测试；
- 第 4 周下半：UAT 验收 → 出测试报告 → 达到门禁放行上线。

**排期红线**：提测延迟不得压缩测试期——测试期被压缩时必须在测试报告中书面声明风险，交团长与用户决策，禁止默默带病放行。
