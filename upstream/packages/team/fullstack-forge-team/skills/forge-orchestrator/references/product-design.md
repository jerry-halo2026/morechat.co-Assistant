# 产品设计规范（product-design）

> 适用角色：产品主理人（product-manager）
> 用途：把选型结论转化为可研发、可测试的产品定义。上游输入：`requirement-analysis.md` 的需求池与 `platform-selection.md` 的选型结论。

---

## 一、PRD 标准模板

PRD 必须包含以下 7 个章节，缺章节视为未完成：

### 1. 背景
- 为什么做：业务问题/机会是什么（2~4 句话）；
- 依据：引用需求确认结论（目标用户、核心场景、预算与时间约束）。

### 2. 目标
- 业务目标：上线后要达成什么（如"首月 500 个预约订单"）；
- 北极星指标：1 个能代表产品核心价值的指标（如"周预约完成单量"）；
- 成功度量：目标值 + 统计口径 + 数据来源。

### 3. 用户故事
- 按 `requirement-analysis.md` 的用户故事模板列出 MVP 全部故事；
- 每个故事标注角色、优先级（P0/P1/P2）与验收标准。

### 4. 功能清单
表格化，逐项可追溯：

| 编号 | 功能 | 描述 | 优先级 | 所属端 | 关联故事 |
|------|------|------|--------|--------|----------|
| F-01 | 预约下单 | 选门店/服务/时段并支付 | P0 | 小程序 | US-03 |

### 5. 流程图说明
- 核心流程逐条用文字+步骤图说明（登录流程、下单流程、退款流程…）；
- 每条流程必须含**异常分支**：网络失败、未登录、库存/时段冲突、支付失败、审核驳回后的去向；
- 流程中每个节点的出口必须明确："到这一步之后用户去哪"不允许留白。

### 6. 数据需求
- 核心数据实体（用户、订单、商品/服务…）与关键字段；
- 需要统计的指标与埋点事件（对应第 2 章成功度量）；
- 后台管理需要的最小运营功能（增删改查、导出）。

### 7. 验收标准
- 每个功能项的可测量通过条件（正常 + 异常）；
- 整体验收口径：核心流程全通过、P0 缺陷为零；
- 明确"不在本期范围"的负向清单，防止验收扯皮。

## 二、功能优先级 P0/P1/P2 判定标准

| 级别 | 判定标准 | 允许数量级 |
|------|----------|------------|
| P0 | 没有它产品核心价值不成立 / 闭环断裂 / 法定与安全要求（隐私协议、实名等） | 通常 30%~50% 功能点 |
| P1 | 显著提升核心体验或转化，缺失时闭环仍可走通 | 次要主力 |
| P2 | 锦上添花（个性化、美化、效率优化），推迟无伤 | V1.1+ |

判定测试三问：
1. 砍掉它，核心闭环还能走通吗？——能走通就不是 P0；
2. 上线首月没有它，用户会流失吗？——会流失是 P0/P1 边界，用数据场景论证；
3. 它是"必备合规"吗？——隐私政策、支付合规等强制项直接 P0。

**红线**：全 P0 = 没有优先级。出现全 P0 必须重分；P0 数量超过功能点 60% 时也要重新审视。

## 三、用户流程设计要点

1. **入口唯一**：每个任务有明确的最佳入口路径，其余入口（分享、搜索）也必须能到达同一闭环；
2. **步骤最短**：核心路径操作步数控制（下单类 ≤4 步），每多一步都要给出理由；
3. **状态可见**：等待、成功、失败、处理中都有明确反馈；禁止"点了没反应"的状态；
4. **失败可挽回**：支付失败→可重试；表单填错→定位到字段并保留已填内容；取消操作→可撤销或二次确认；
5. **新用户零门槛**：首访不需要学习就能完成核心动作；注册/登录尽量后置（先体验后登录），必须登录时给出理由；
6. **异常即设计**：把"没网怎么办、数据为空怎么办、权限被拒怎么办"写进流程，而不是留给开发即兴发挥。

## 四、多端版本路线图（V1.0 MVP → V1.1 迭代）

### V1.0 MVP（首版本）
- 范围 = 全部 P0 + 少量决定转化率的 P1；
- 单端或最小组合先行（引用选型结论）；
- 上线标准：核心闭环可用 + 基础数据埋点 + 合规项齐全。

### V1.1（上线后 2~6 周内）
- 依据 V1.0 数据决定：留存/转化瓶颈在哪，补对应 P1；
- 修复 V1.0 收集的高频反馈；
- 扩展第二端（如小程序验证成功后上 App）。

### V1.2+
- P2 功能按数据排序逐版消化；
- 引入兴奋型功能（差异化竞争点）。

路线图呈现要求：每个版本给出目标、范围（功能编号）、成功指标、大致时间窗；**版本间范围不重叠**，防止范围蠕变。

## 五、需求变更管理

上线前后需求都允许变更，但必须走流程防止失控：

1. **变更登记**：任何新增/修改/删除记入需求池，标注提出人、日期、影响评估（范围/工期/成本/已开发部分）；
2. **影响评估**：区分"未开发"（直接调整优先级）与"已开发/在开发"（评估返工量，必要时给出替代方案）；
3. **版本归属决策**：新需求默认进下一个版本，除非属 P0 级闭环缺失或合规问题才允许插入当前版本；
4. **用户确认**：影响工期或成本的变更必须经用户确认后执行，记录确认结论；
5. **变更通知**：变更生效后同步给所有受影响阶段（研发、测试、上架材料），保证口径一致。

**变更红线**：禁止口头变更；禁止在开发中途静默修改验收标准；累计变更导致工期偏差超过 30% 时必须重新评估整体计划。

## 六、信息架构与页面清单

PRD 的流程章节须配套页面清单，保证"每个流程每一步都有页面承接"：

| 页面编号 | 页面 | 层级 | 承载功能 | 优先级 |
|----------|------|------|----------|--------|
| P-01 | 首页 | 1 | 服务入口、活动位 | P0 |
| P-02 | 门店列表 | 2 | 筛选、距离排序 | P0 |

设计要点：
1. 页面清单与功能清单互相引用（功能必须有页面、页面必须服务功能），出现"孤儿页面"或"无页面功能"即结构性缺失；
2. 导航结构先定（底部 Tab ≤5 个，或后台侧边导航分组），再铺页面，避免后期重构；
3. 每个页面标注四个关键状态：空态、加载态、错误态、无权限态。

## 七、数据需求与埋点细化

对应 PRD 第 6 章，埋点按"指标反推事件"方式定义：

1. 北极星指标 → 拆解为可统计事件（如"周预约完成单量" = 预约提交事件 × 支付成功状态）；
2. 事件命名规范：`模块_动作`（如 `order_submit`、`pay_success`），全团队统一口径；
3. 每个事件定义属性：时间、用户ID、来源渠道、关键业务参数；
4. 关键漏斗逐段埋点：曝光 → 点击 → 提交 → 成功，漏斗断点就是下一步优化点；
5. 输出埋点表：事件名 / 触发时机 / 属性 / 对应指标——研发据此开发、测试据此验证。

## 八、PRD 自检清单

提交前逐项核对：

- [ ] 背景与目标含可度量的成功指标（有数值、有统计口径）
- [ ] 每个用户故事有角色、场景、验收标准
- [ ] 功能清单无全 P0，P0 占比 ≤60%
- [ ] 每个功能有验收标准且可测量（禁止"体验良好"式描述）
- [ ] 核心流程含异常分支，无流程断点（每步都有出口）
- [ ] 页面清单覆盖全部功能，页面标注四态
- [ ] 数据需求含埋点表与指标口径
- [ ] 版本路线图各版本范围不重叠
- [ ] 明确列出"不在本期范围"清单
- [ ] 与选型结论一致（端组合、目标用户、预算约束未私自变更）

## 九、常见 PRD 反模式

1. **散文式描述**：大段文字无结构——研发与测试各自理解，一律改用表格与编号；
2. **验收标准缺位**：只写"做什么"不写"做到什么程度"——验收时必然扯皮；
3. **异常分支留白**：只画阳光路径——线上大部分 bug 出在异常分支；
4. **需求与页面脱节**：功能清单里的功能找不到页面承载；
5. **版本计划拍脑袋**：V1.0 塞满所有想法——回到 MVP 四原则重新裁剪；
6. **变更不记录**：口头一句"改一下"——两周后没人记得为什么改、改了什么、谁确认的。

## 十、跨端一致性设计要点

多端产品（引用选型组合）的一致性策略：

1. **信息架构一致**：核心任务在各端的完成路径语义一致（入口命名、业务术语统一）；
2. **交互习惯随端**：桌面用悬停/快捷键、移动端用手势/长按、小程序用微信授权链路——不强行照搬桌面设计；
3. **能力降级预案**：同一功能在能力弱的端提供替代方案（App 有推送、小程序用订阅消息、H5 用短信）；
4. **数据同源**：多端共用一套账号与业务数据；跨端状态（购物车、草稿）明确定义是否同步，写进 PRD；
5. **视觉令牌统一**：色彩、字号、圆角、间距用统一设计令牌，各端映射实现，避免"三端三个设计语言"。

## 十一、版本路线图示例（门店预约小程序）

以下示例展示"范围不重叠 + 数据驱动迭代"的写法：

**V1.0 MVP（第 1~6 周）**
- 目标：跑通"预约→支付→核销"核心闭环，验证复购率
- 范围：门店浏览（F-01）、时段预约（F-02）、在线支付（F-03）、核销码（F-04）、简易后台（F-05）
- 成功指标：首月预约完成单量 ≥300；次周回访率 ≥25%

**V1.1（上线后 2~6 周，按数据决策）**
- 目标：修补 V1.0 留存/转化瓶颈
- 范围候选：取消/改期流程（投诉高频则进）、会员卡（复购数据好则进）、订阅消息提醒（爽约率 >15% 则进）
- 决策规则：每项候选功能对应一个 V1.0 指标触发条件，数据说话

**V1.2+（Q+1）**
- 范围候选：积分体系、分销裂变、多门店连锁版
- 原则：全部为 P2/P1 存量，逐版消化不并行

**刻意不做（负向清单）**：直播带货、社区动态、AR 试穿——与核心闭环无关，防止范围蠕变。
