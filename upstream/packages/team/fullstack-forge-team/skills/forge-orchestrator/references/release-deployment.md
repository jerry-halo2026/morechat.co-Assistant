# 上线发布手册（release-deployment）

> 适用角色：上线发布师（release-manager）
> 用途：把通过质量门禁的版本安全、可回退地发布到各端。上游输入：技术方案（部署形态）、测试报告（质量门禁结论）。

---

## 一、CI/CD 基础流程

```
代码提交 → 自动构建 → 单元测试/Lint 卡点 → 制品打包（带版本号）
   → 自动部署到开发环境 → 冒烟通过
   → 部署测试环境 → 自动化回归
   → 人工确认 → 部署预发环境 → 验证（连生产库影子或只读）
   → 发布审批 → 生产环境（灰度/分批） → 全量
```

关键卡点：
1. 构建失败或测试不过，禁止流入下一环节；
2. 制品唯一：生产运行的包必须来自 CI 产出的同一制品，禁止本地打包直传生产；
3. 版本号规范：`主.次.修订`（如 1.0.0），每次发布可追溯（版本号 + git commit）；
4. 回滚制品保留：至少保留上一稳定版本制品，随时可切回。

## 二、部署方案对比

| 方案 | 优势 | 劣势 | 适用 |
|------|------|------|------|
| 云服务器（ECS/CVM） | 完全可控、成本可预估 | 需自运维、扩容要操作 | 常规业务、有运维能力 |
| Serverless（函数/云托管） | 免运维、按量付费、天然弹性 | 冷启动、长任务受限、锁定风险 | 流量波动大、小团队快速上线 |
| 静态托管（OSS+CND / Vercel 类） | 极廉价、高可用、秒级发布 | 仅前端/静态内容 | 官网、纯前端应用、文档站 |

**组合基线**：前端静态托管 + 后端 Serverless/云服务器 + 云数据库（托管版）+ 对象存储 + CDN，是中小项目成本与稳定的最优解。组合基线的一个现成落点是腾讯云 CloudBase：静态托管 + 云函数 + 云数据库 + 对象存储在一个环境内，免自运维。

环境划分（必备四套）：开发 → 测试 → 预发（接近生产配置）→ 生产；配置与密钥按环境隔离，生产密钥不进代码库（用云 KMS/环境变量注入）。

## 三、应用商店发布

### 3.1 App Store（iOS）
- 前置：Apple Developer 账号（$99/年）、证书与描述文件、Bundle ID 与代码一致；
- 审核要点（高被拒项）：
  - 隐私：App Privacy 清单如实填写、权限申请文案明确用途（相机/定位/相册/麦克风）；
  - 支付：虚拟商品（会员、金币）必须走 IAP，实物/服务可用第三方支付；
  - 元数据：截图与实际功能一致、描述不含"测试版/Beta"、无诱导性外链；
  - 账号：含第三方登录须支持 Sign in with Apple；含 UGC 须有举报与屏蔽机制；
  - 完整性：空白页、占位功能、"敬请期待"会被拒；
- 周期：首审通常 1~7 天，被拒后修改重提重新排队——**排期必须预留被拒重来一次的时间**；
- 提审技巧：提供演示账号 + 审核备注（说明隐藏功能如何体验）、避免大版本首审赶节日（审核积压）。

### 3.2 华为应用市场（鸿蒙/安卓）
- 鸿蒙应用走 AGC（AppGallery Connect）：创建项目 → 配置签名 → 提交审核；
- 审核要点：隐私政策与应用行为一致、权限最小化、应用信息与资质一致、元服务规范；
- 安卓侧：华为、小米、OPPO、vivo、应用宝各家材料略有差异（软著、承诺函、隐私链接），准备一份标准材料包复用。

### 3.3 微信小程序
- 类目与资质：按服务类目提供资质（电商→EDI/ICP 或平台资质、医疗→行业资质、餐饮→食品经营许可等），**类目选错是首发被拒主因**；
- 服务器域名：request/upload/download 域名须备案 + HTTPS，提前在小程序后台配置并留出生效时间；
- 审核要点：页面功能完整可用、不得诱导分享、虚拟支付 iOS 受限、用户隐私保护指引必须填写；
- 版本流程：开发版 → 体验版 → 提交审核（1~7 天）→ 发布全量；可配灰度（按比例放量）。

### 3.4 网站 / 后台
- 大陆服务器：ICP 备案完成前不得解析上线（备案期间可用境外/香港服务器临时验证，正式上线必须备案）；
- HTTPS 证书部署、域名解析、SEO 基础（robots/sitemap）。

## 四、灰度发布与回滚方案

### 4.1 灰度策略

| 端 | 灰度手段 |
|----|----------|
| 服务端 | 按比例分流（Nginx weight / 网关灰度）→ 按用户标签（内部员工→白名单→5%→50%→全量） |
| 小程序 | 微信后台按比例发布，观察 1~2 天再全量 |
| App | 分阶段发布（Phased Release 7 天自动放量）/ 分渠道分批上架 |
| Web 前端 | CDN 版本目录切换，秒级回退 |

每阶段观察指标：错误率、崩溃率、核心转化率、客诉量；指标异常立即暂停放量或回滚。

### 4.2 回滚方案模板（必填）

```
回滚触发条件：错误率 >1% 或 P0 bug 出现或核心转化跌幅 >20%
回滚步骤：
  1. 服务端：切换回上一版本制品（命令/控制台路径写明），预计 5 分钟
  2. 客户端：App 无法物理回滚 → 服务端接口兼容旧版本 + 关闭新功能开关
  3. 数据库：结构性变更必须向后兼容（先加后删），禁止破坏性变更上线
回滚验证：核心接口探活 + 核心链路冒烟
通知机制：用户公告模板 + 客服口径
```

## 五、上线检查清单（Checklist）

- [ ] 质量门禁结论通过（P0 bug=0、核心链路 100%）
- [ ] 生产配置核对：数据库连接、第三方密钥、支付回调地址、推送证书
- [ ] 证书/签名核验：iOS 证书在有效期、安卓签名与加固兼容、HTTPS 证书覆盖所有域名
- [ ] 域名白名单：小程序 request 域名、App 备案域名一致
- [ ] 备案/资质生效：ICP 备案、行业类目资质
- [ ] 隐私合规：隐私政策链接可访问、权限文案正确、隐私清单与实际一致
- [ ] 监控告警已接入：错误率、崩溃率、核心业务指标（联动运维保障方案）
- [ ] 回滚方案已演练或走查（触发条件、步骤、责任人明确）
- [ ] 发布时间窗确认（避开业务高峰、避开节假日审核积压）
- [ ] 应急联系人到位（发布窗口内可响应）

## 六、证书签名常见坑

1. **iOS 证书**：发布证书与描述文件不匹配、Bundle ID 拼写不一致、证书过期（提前 30 天续期）、Transfer App 后签名链断裂；
2. **Android**：正式签名与调试签名混淆、渠道包签名不一致导致覆盖安装失败、加固后未重新签名、应用升级签名不一致导致无法更新（不可逆，**首版签名务必用可长期保管的正式 keystore**）；
3. **小程序**：域名未备案或非 HTTPS、白名单漏配 upload/download 域名、基础库版本不兼容新 API；
4. **HTTPS 证书**：证书链不完整（部分安卓机报错）、多域名漏配、到期未自动续期（配监控）；
5. **支付回调**：回调地址外网不可达（安全组/防火墙）、签名验证失败、重复回调未幂等。

每个坑都必须出现在上线检查清单的核验项里，禁止凭记忆临场检查。

## 七、各端发布流程速览

### iOS App
准备材料（证书/描述文件/截图）→ 构建上传（Xcode/Transporter）→ App Store Connect 填写元数据与隐私清单 → 提审 → 通过后选"手动发布"或自动发布 → 可选分阶段发布（7 天自动放量）。

### 鸿蒙 / 安卓
AGC/各家商店创建应用 → 上传签名包 → 填写资质与隐私材料 → 提审 → 通过后发布（可分渠道分批放量）。

### 微信小程序
代码上传（开发工具/CI）→ 提交审核（填功能页与演示视频）→ 审核通过后发布（可配按比例灰度）。

### 网站 / 后台
构建产物 → 预发环境验证 → 生产部署（蓝绿或滚动）→ 冒烟验证 → 切流全量；域名/证书/备案状态前置核验。

## 八、审核被拒应对手册

被拒是常态，应对原则：**读懂拒绝理由 → 定位根因 → 修复或申诉 → 带着证据重提**。

| 拒绝原因 | 典型措辞 | 应对 |
|----------|----------|------|
| 崩溃/无法使用 | "We found… crashed" | 按审核员描述的设备复现并修复；备注写明修复点 |
| 隐私问题 | 权限用途不明/收集过度 | 修改权限文案、砍掉非必要收集项、补全隐私清单 |
| 支付问题 | 虚拟商品未用 IAP | 数字内容改 IAP 或移除购买入口（实物与服务除外） |
| 功能不完整 | 空白页/占位/敬请期待 | 砍掉未完成功能的入口，或补齐后再提 |
| 类目/资质 | 缺少资质证明 | 补资质材料或调整类目（小程序首发高发） |
| 元数据不符 | 截图与实际功能不符 | 更新截图与描述，如实一致 |
| UGC 缺管控 | 无举报/屏蔽机制 | 补举报入口、敏感词过滤、黑名单后再提 |

申诉要点：在 Resolution Center 回复，语气客观、附修复证据（截图/说明），不与审核员争辩规则。每次被拒记入"被拒台账"（版本/原因/处理），同类问题不得二次出现。

## 九、版本管理与更新策略

1. **版本号**：`主.次.修订`——大功能或破坏性变更升主版，常规功能升次版，缺陷修复升修订；
2. **更新节奏**：小程序审核通过即可发；App 控制在每 2~4 周一个版本，攒批发布降低审核与用户升级成本；
3. **强更策略**：只对"安全/合规/阻断性缺陷"使用强制更新，其余用软引导（更新弹窗 + 应用市场跳转）；
4. **兼容承诺**：服务端接口对新旧客户端向后兼容至少 2 个版本，为用户升级留时间；
5. **发布窗口**：避开业务高峰（大促、节假日峰值），选工作日上午发布，留足当天观察与响应时间。

## 十、发布沟通与公告

- **对内**：发布单（版本内容/时间窗/责任人/回滚预案/检查清单结果）提前 1 个工作日发出并确认；
- **对用户**（涉及体验变化时）：站内公告或推送；应用商店更新说明（What's New 写用户价值，不写内部术语）；
- **客服口径**：本次发布的已知问题与应对话术，发布前同步客服；
- **事故口径**：回滚或故障时的对外说明模板提前备好——发生了什么/影响范围/当前状态/补偿方案。

## 十一、上线后 72 小时观察

| 时点 | 检查项 |
|------|--------|
| T+30min | 核心接口错误率、支付成功率、崩溃率与基线对比 |
| T+2h | 商店/小程序后台无新增异常反馈；监控告警已完成静默期核对 |
| T+24h | 业务指标（订单/注册/活跃）无异常波动；客诉量正常 |
| T+72h | 发布复盘：清单执行偏差、告警误报调优、用户反馈 Top3 进入需求池 |

72 小时内出现 P0 级问题 → 立即触发回滚预案，并同步团长与用户；观察结论作为运维方案（ops-monitoring.md）的输入。

## 十二、发布材料归档规范

每次发布完成后归档以下材料，保证可追溯、可复盘、可交接：

1. **发布单**：版本内容、时间窗、责任人、检查清单执行结果（含未通过项的豁免说明）；
2. **制品记录**：版本号、git commit、构建产物存放位置、上一稳定版本制品位置（回滚用）；
3. **审核记录**：各端提交/通过/被拒时间线，被拒台账同步更新；
4. **配置变更记录**：本次上线涉及的配置、密钥轮换、白名单、证书变更；
5. **观察报告**：72 小时观察结论（联动第十一章）。

归档纪律：材料在发布完成 24 小时内归档；未归档的发布视为未完成；归档材料随版本保留至少 1 年。
