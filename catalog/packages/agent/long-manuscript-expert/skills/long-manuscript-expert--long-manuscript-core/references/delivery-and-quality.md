# 产物、阅读设计与交付复核

## 一、默认交付合同

主要交付是一份可编辑的研究底稿，以及与正文对应的来源、写作建议和续改信息。短任务可合并在一份作品中，长项目可拆为主稿和关联附件，不要求用户维护内部表单。

### 主底稿

- 研究问题、读者、范围、资料截至时点和主要发现；
- 按研究问题组织的实质章节，而非固定模板；
- 数据、案例、比较、机制解释、反证、不确定性和限制；
- 正文就近引用，附录提供精确来源定位；
- 当前版本、已完成范围和未完成范围。

### 来源与证据

按需列出本地和网络出处、资料类型、实际访问深度、日期或版本、页段或单元格或媒体时间、来源家族及派生关系。网络出处优先使用来源官方或原生的规范直达 URL，去掉无关推广和跳转参数；无法确认规范地址时保留实际可读地址并说明。本地出处给可打开的绝对路径或宿主导航链接，并附具体页段、表名与行列、单元格或媒体时间位置，不能只写文件名或整篇长论文。内部工作记录与读者来源附录分开，不能把文件清单当作全部证据。

### 写作建议

说明目标读者与主线、章节取舍、材料如何使用、适合的图表、需要克制的表述和待补内容。建议必须针对本稿及材料，不能复制通用写作清单。

### 继续与修订

说明当前版本、材料变化、受影响章节、保留内容、失败或未知项和唯一下一步。继续时能从该状态推进，而非重新制定整项计划。

## 二、阅读与视觉基线

- 专业、克制、适合长读；用户已有模板和品牌优先。
- 正文、标题和说明层级清楚，标题原则上不超过三级；浅色背景、深色正文、少量低饱和强调色，含义不只靠颜色。
- 表格写清单位与期间，数字精度一致；长表保留表头，宽表拆分或适配，不截断关键内容。
- 图表只用于解释问题，轴、单位、样本、期间和来源完整，不混合不可比指标。
- 反证与缺口用明确文字标签，不能藏在低对比颜色或复杂筛选器后。
- 图片与媒体证据注明用途、来源和页码、区域或时间位置。生成图、示意图与原始证据严格区分。
- 长 URL、本地完整路径和技术摘要放在来源附录或工作记录，不打断正文。

用户指定 Word、PDF、Markdown、HTML 或其他格式时以目标为准。用户已指定 Markdown 与 HTML 等开放格式时直接完成对应交付和检查，不无必要启动 Word 重流程或额外交付链。未指定时，使用当前可用的文档、图表和交付能力提供可编辑主稿及稳定阅读呈现；同一文件的宿主预览已满足时，不为凑格式重复生成。当前会话没有可验证的文件写出能力时，上述文件型交付不适用：改为在对话中交付可直接复制的正文与便携接续卡，文件写出、读回与预览保持未完成，不把聊天内容称为已保存文件。路径与输出格式按执行器实际环境表达，不把用户自报的客户端平台当作执行器 OS。

## 三、分层交付检查

以下状态分别记录：

1. **内容完成**：研究问题已有实质回答，关键缺口和反证没有被排版隐藏；
2. **文件生成**：目标路径确有文件，格式和扩展名正确；
3. **文件回读**：重新打开并读取，确认不是空文件或旧版本；
4. **内容一致**：正文、表格、图表、摘要、引用和版本来自同一稿件，数字与对象关系口径一致，空字段未填假值；存在已知未同步内容时准确列出，不宣称全稿一致；
5. **打开预览**：实际在目标宿主或交付表面发起打开，记录成功、失败、受阻或未知；发起打开不等于已经看到画面；
6. **实际视觉查看**：模型或复核者确实看到渲染结果后，记录查看了哪些页面、帧、表格或附录及未覆盖范围；截图未产生时写未产生，不能写已查看；
7. **视觉检查通过**：仅对实际看到的范围检查标题、正文、宽表、长链接、图表和附录后给出结论；需要 PDF 或打印时再查分页和跨页表头；
8. **用户可用**：用户能打开、阅读、编辑或下载，入口明确；
9. **用户采用与效果**：只有真实采用或后续证据才能评价，不能从文件生成推断收益。

文件存在不证明回读成功，回读成功不证明打开预览，打开预览不证明实际视觉查看，实际查看也不自动等于检查通过；视觉合格不证明事实真实或用户采用。无法预览时交付已可靠完成的文本或文件，并明确“视觉预览未验证”。

## 四、自动预览预算与真实状态

同一自动预览路线默认只有初试和最多一次有依据重试。路线由交付物、预览方法和预先声明的工作单元共同确定；输出路径、截图文件名或重命名工作单元不产生新预算。计划内多帧采样在开始前声明各工作单元，与失败后的重试分开记录，不能用“下一帧”名义重试同一失败单元。

1. **初始化**：首次自动预览前建立路线和全部计划工作单元，默认每单元一次初试、整路线最多一次失败重试。包内 `scripts/preview_budget.py` 是可选的标准库守卫；宿主可执行时，先用 `init` 建立状态，后续每次调用必须取得 `authorize` 的允许结果。已有状态文件不得重新 `init` 清空或重置预算，守卫未实际运行不得声称已使用。
2. **调用前消费**：每次调用前先追加一条授权记录，取得尝试 ID 后才启动预览。没有授权、预算已用尽、路线内仍有未解决的状态未知或路线已停止时不得启动；该封锁适用于新初试和重试，不能换预声明单元或输出路径规避。宿主不能执行守卫时，使用同字段的顺序工作记录实施相同拒绝规则，并标注“手工预算记录”，不能虚报脚本执行。
3. **调用后记录**：按实际结果记录调用返回、明确失败或状态未知，以及截图/产物的已生成、未生成或未知。失败原因没有证据时保持未知，不强行归因于沙箱、权限、网络或模型；不得通过降低浏览器保护设置反复试错。
4. **未知确认与恢复**：任何 `unknown` 在 `status` 的 `unresolved_unknown` 中保持未解决；取得原调用结果的具体证据后，用 `resolve` 在原尝试上追加 `resolution`，不得改写原 `outcome: unknown`、`artifact_state: unknown` 和后续确认历史。确认已返回且产物已生成后可按原计划继续；确认失败或已返回但产物未生成后，才按原初试 ID 申请仅有的一次重试。`resolve` 只补录证据，不执行或重启原调用。
5. **有依据重试**：只有前次已明确失败或已返回但必要产物未生成时，才可为同一工作单元申请唯一一次重试，并写明与实际结果对应的理由；包括状态未知经证据确认后的对应结果。状态未知先检查原操作，不盲目重试；重试必须关联原尝试 ID，不得换工作单元或输出路径规避。
6. **停止即封闭**：宣布停止时立即把路线标为停止，此后不再授权同类调用，也不能换一个输出路径继续。无法确认的状态未知可直接安全停止；停止后仍可用 `resolve` 补录迟到证据，但不重新开放路线。交付稳定文本或已可靠生成的文件，并明确未验证范围。
7. **次数来自日志**：最终答复、交付说明和复核从执行记录汇总初试、重试、计划内各工作单元及总数，不靠回忆。`status` 分开报告待完成、未解决未知和已确认未知；预算记录只证明调用控制，不证明文件存在、视觉查看或质量通过。

同一状态文件只能由主专家顺序维护，不得交给并行分支或多个进程竞争写入；并行分支只返回结果，由主专家按顺序记录。当前没有并发写入或崩溃恢复实证，不得声称具备这些能力，也不为此扩展复杂调度器。

从专家根目录使用守卫时，单工作单元的基本顺序如下；多帧计划在 `init` 时重复传入 `--unit` 一次声明完整。只有 `authorize` 返回 `status: authorized` 且退出码为 0 才能启动对应预览，拒绝结果不得启动：

```bash
python skills/long-manuscript-expert--long-manuscript-core/scripts/preview_budget.py init --state preview-state.json --route final-html:host-preview --unit main
python skills/long-manuscript-expert--long-manuscript-core/scripts/preview_budget.py authorize --state preview-state.json --unit main
# 仅在上一条授权后执行一次宿主预览；随后按实际结果记录，不把 returned 当作视觉通过。
python skills/long-manuscript-expert--long-manuscript-core/scripts/preview_budget.py complete --state preview-state.json --attempt-id 1 --outcome failed --artifact-state missing --note "实际返回信息；原因未知则明确写未知"
# 仅前次符合失败条件且有依据时申请一次同单元重试。
python skills/long-manuscript-expert--long-manuscript-core/scripts/preview_budget.py authorize --state preview-state.json --unit main --retry-of 1 --reason "与实际失败对应的重试依据"
python skills/long-manuscript-expert--long-manuscript-core/scripts/preview_budget.py stop --state preview-state.json --reason "达到预算或交付方决定停止"
python skills/long-manuscript-expert--long-manuscript-core/scripts/preview_budget.py status --state preview-state.json
```

若尝试 1 实际记录为 `unknown`，不得执行上例重试；取得原调用结果的具体证据后改用以下命令。无法取得证据时直接 `stop`，不得换单元、换输出路径或重新 `init`：

```bash
python skills/long-manuscript-expert--long-manuscript-core/scripts/preview_budget.py resolve --state preview-state.json --attempt-id 1 --outcome returned --artifact-state generated --evidence "原调用结果的具体证据定位"
python skills/long-manuscript-expert--long-manuscript-core/scripts/preview_budget.py status --state preview-state.json
```

最小工作记录如下；守卫状态文件或等效手工记录均可，但必须能回查：

| 路线/工作单元 | 计划类型 | 尝试 ID/关联初试 | 调用前授权与时间 | 调用结果 | 产物状态 | 重试依据或停止原因 | 正文/交付说明消费 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 交付物+方法/预先命名单元 | 计划初试/失败重试 | 实际序号 | 已授权/拒绝及时间 | 返回/失败/未知 | 已生成/未生成/未知 | 实际理由；无则未知 | 实际说明位置 |

## 五、独立复核清单

优先检查能改变结论或交付的高风险项：

- 关键主张是否有实际读到的来源支持，定位是否正确，限定和否定是否保留；
- 对象身份、功能替代性、商务权益等价和可比较维度是否分别回到原始值和直接依据；已有映射是否被消费，身份不同是否被误推为不可比较，正文与关系表是否双向一致；
- 同文相反结果、限制和适用条件是否被遗漏，摘要数值是否仍带样本、时期、语言、指标、分母和版本等关键条件；
- 效果指标是否具备同口径前后测及独立定位；缺前测是否仍被写成变化，未报告统计检验是否被误写为持平、随机波动或无效，观察差异、统计判断、实际意义和采购建议是否分层；
- 来源是否独立，转载、同研究多报告和媒体派生物是否被误算；
- 数字是否同对象、同单位、同期间、同分母，公式与输入能否复算；字段数、重复数和分母是否实际计算，范围性事实是否被压缩成普遍事实；
- 推断、作者判断、假设和示例是否被误写成事实，缺少证据、未读取、未报告和不存在是否被混用；
- 反证、竞争解释和证据缺口是否可见；
- 补料是否只更新受影响范围，作者手改和旧稿是否保留，新料变化与原稿旧错是否分开；
- 多格式是否同版，最终字数是否按最终文件和明示口径重算，交付说明是否把未执行、失败或受限写成通过；
- 自动预览是否在调用前消费预算，计划内多帧与失败重试是否分开，停止后是否仍有同类调用，最终次数是否来自日志，文件存在、打开预览、实际视觉查看和检查通过是否分层。

复核任务必须让复核者取得必要原件或实际可访问的原始定位，并给出明确待答问题、受影响主张、检查范围和所需返回证据；不能只把主稿摘要交给复核者。复核问题需有证据定位、受影响主张、修复或翻案条件和复测状态。结构校验只能证明结构，语义复核必须回到原件；模型自评只能作为查缺线索，不能替代原生用户任务验收。

交付前至少抽查一项关键比较、一项效果或数字主张和一项范围限制，分别完成“最终正文 → 核对记录 → 原始材料”与“原始材料 → 核对记录 → 最终正文”。有原生协作能力且适合时，可把明确问题和必要原件交给独立复核分支；无此能力时记录为本执行链的顺序复核，不伪称独立多智能体。

## 六、最终文件计数与排版后复核

- 字数、行数、表格数和附录范围以最终交付文件为输入，不以草稿、中间 HTML 或记忆中的计数替代。
- 用户可见说明必须写清计量口径：正文是否含标题与表格，附录是否排除，Markdown 标记、HTML 标签、代码和脚注如何处理；不同口径分别报告，不混成一个无解释数字。
- 后续排版、格式转换或任何正文编辑后，重新执行相关计数、文件回读、关系/主张一致性及视觉检查。旧计数和旧预览回执不能绑定新文件。

## 七、状态措辞

- 对尚未执行的项目写“未执行”及原因；
- 对当前能力或授权不足写“受限”，说明影响和替代结果；
- 对明确失败写“失败”，保留已完成的可靠部分；
- 对无法确认的运行或外部状态写“未知”，不盲目重试；
- 只有当前任务真实证据覆盖的项目写“通过”，同时说明验证范围；
- 专家候选生成、本地校验、新会话加载、市场更新和正式上架是独立阶段，不互相推导。

## 八、前台进度、冷启动与成本分层

- 前台按“整理证据—形成正文—排版—核对交付”表达已经发现什么、正在形成什么、还剩哪些缺口；不把 `full_pipeline`、S1/S2/S3、Stage 或内部状态协议暴露为用户进度。
- 长任务尽早给出一项有依据的发现、材料到问题的映射或阶段正文，不连续只报“准备、读取、准备撰写”。模型切换后继续使用用户语言，中文任务保持简体中文，并复用仍有效的材料和核验结果。
- 涉及时耗时，分别记录宿主启动、模型等待、工具执行、生成或写作、渲染和人工复核；平台排队不能写成已开始研究，单个总耗时不能用于推断各层原因。
- 涉及成本时，把专家生成、生成期预演、生成方复核、独立产品验收和用户实际研究任务分开。不得把多阶段合计称为专家单次研究成本；实际积分或外部费用不可见时保持未知。
- 在能完成合格任务的路线中优先低积分方案，但不省略承重证据和必要检查。不得从 `0.00x` 标签推导全程免费，也不得由某个模型一次失败推广为所有模型不可用。
