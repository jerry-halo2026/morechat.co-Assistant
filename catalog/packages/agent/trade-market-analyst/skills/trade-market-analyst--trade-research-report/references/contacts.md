# 联系方式六项：公司和本人必须先明确

当前实现按网址/公司找邮箱、按姓名/关键人找邮箱、按姓名/关键人找手机六项（O2）。任务标题与完整提示词来自业务目录，不能把“找手机”改成已确认手机的承诺。单主体计划支持 chat/xlsx，不扩成任职核验、应用开通核验或邮箱验证。每个输入主体独立建计划与查询记录；批量逐项运行并选择聊天+Excel，没有跨任务共享预算或合并总账本。仅换格式不重查。

## 快速通道（先判断）

六项（一家或多家公司）用户没要 Excel 或其他文件时走这里；要文件走下文完整流程。不调 `plan_report`、`get_balance`、`get_render_spec`，不用 `task_run.py` 建日志，不写结果文件。

1. 钉主体：缺公司/官网、指定姓名或目标角色先问。用户给了官网直接用；按公司找邮箱只给了公司名时先 `find_company_website`（1 点），候选里只有一个明显是本公司才直接用，同名、多国站或拿不准就列出候选让用户选，不取第一条。找人时有官网传 `domain`，没有就传 `company`；返回的人混着几家同名公司时先问是哪一家，不硬选。
2. 报总价确认一次：一句话说清要查几家、几人、预计多少点——官网 1 点、官网邮箱 2 点；找人每家一页最多 100 联系人点；取邮箱每人 10、电话每人 30 联系人点。用户同意后一口气查完，中途不再停；只用普通点的官网与官网邮箱查询只告知不等确认。
3. 查询：
   - 按网址/公司找邮箱：`find_emails_by_domain`（默认 50 条）。
   - 按姓名找：`find_contacts` 查全部职级的一页 20 人，在返回里按姓名和公司对上本人；同名多行或对不上就停下问，不换别人。
   - 按关键人找：`find_contacts` 的 `job_function` 只填一个职能（采购→Purchasing、销售→Sales、运营→Operations，其余按工具职能表）；按返回的真实职位选最多 3 人（显式数量优先），职位与角色对不上的不选。角色是采购但这一页没有职位带采购用词的人，先告诉用户，问是否再查一页 Operations（另最多 100 点）找供应链职位。
   - 取联系方式：选中人员的主页交 `get_contact_emails`（一次最多 10 人）或 `get_contact_phones`（一次最多 5 人）。
4. 聊天里直接给结果，一人几行、多人一张表：公司、官网、姓名、职位、主页、邮箱及类型（企业/个人）或电话及类型、状态（已取得 / 未取得及原因）、实扣点数（普通点和联系人点分开，读每次响应的 `billing` 相加）。邮箱写未验证，电话类型没依据写未知，不称手机；占位格式邮箱（`is_pattern_placeholder`）单独标出，不算取得；没找到只说本次未收录，不说不存在。

## 整理请求

先根据已选任务、胶囊或明确意图选择下面闭合请求。缺公司/官网、指定姓名或目标角色须补齐；模板占位不是输入。无须我方产品/委托方。删除输出要求仍保留来源、证据、状态和费用。公司国家可用 constraints.country，含义是公司所在国家，仅用于主体确认与摘要，不作为员工所在地过滤。

| 任务 | task.intent | subject 必填 | 默认范围 |
|---|---|---|---|
| 按网址找邮箱 | domain_emails | domain | 已确认公司官网；公开邮箱默认显示50条、显式最多100 |
| 按公司找邮箱 | company_emails | company | 查官网候选、明确选择后查该官网邮箱；提供domain则跳过付费查官网 |
| 按姓名找邮箱 | person_email | company或domain、name | 仅指定本人，最多1位 |
| 按关键人找邮箱 | role_emails | company或domain、role | 最多3位匹配角色，显式最多10位 |
| 按姓名找手机 | person_phone | company或domain、name | 仅指定本人，最多1位 |
| 按关键人找手机 | role_phones | company或domain、role | 最多3位匹配角色，显式最多5位 |

统一 type=contacts，outputs.profile=O2。constraints.max_contacts 只用于人员任务，constraints.limit 只用于官网邮箱。单人默认chat；邮箱名单/多人默认chat+xlsx，显式1条/1位可默认chat；用户明确的formats优先。多人上限是选取数量，不是检索计费人数，也不要求凑满；本次完成范围以明确选定人员为准，选中但未查询或未取得字段仍披露缺口。

人员任务可带 subject.profile_urls，但仅允许用户实际提供的人员公开主页，仍须明确确认本人、公司和角色后才用；无此输入时先取人员名单。指定姓名按计划检索全部职级的一页20人，没有姓名直筛参数；角色在真实返回职位/职能上核对。一页没找到本人只说明本次未收录或未返回，不证明不存在，不自动缩小职级或改查其他人。

## 计划与两钱包预算

调 plan_report(task=...)，不混旧模块参数。规划本身0点。保存完整计划；普通点按实扣记账不必事先确认；取已授权的联系人点预算，缺少或超预算在付费前合并确认，不造默认授权。套餐授权和账户余额仍以服务端为准，本地预算不等于开通权限。

现价：官网查找1普通点，官网邮箱2普通点；人员检索上限100联系人点（实际按返回人数计，一页20人，每人5点）；取邮箱10/人、电话30/人。3位取邮箱需先考虑100+30联系人点，而非只算3人的检索费用。已确认主页可省名单检索。未查履历，不追加其5/人的调用；没有验证、电话或邮箱的额外授权不能静默追加。取字段失败/空值不能自行推断免计费，全部以每次响应billing实扣为准。

执行与续做按 SKILL.md 第 3 步写查询记录，同参成功不重跑。付费前按上面单价把预计点数告诉用户：联系人取字段允许已选名单的子集，按人数乘单价估算，不得低报。具体调用参数照计划步骤取。

## 选择要明确并记下依据

所有选择写真实确认依据，不使用示例文字冒充用户授权。输入或本会话已有明确公司、官网、本人及预算确认时直接复用并记下，不重复问用户；仅有歧义、缺必填项、预算缺失或超出时合并澄清。选择依据与调用参数留在工作目录，不把工具参数展示给最终业务用户。

1. 付费前确认公司：公司、公司国家和官网范围按计划原样，记下确认依据。
2. 官网来自用户：记下规范化域名与用户的明确确认。来源为查询候选时：指向官网候选响应里的真实行（调用编号、行号、域名）；官网候选是线索，不能自动选第一条或全部挖邮箱。缺官网/同名未确认则停止对应付费步骤。
3. 选人：说明如何确认姓名、公司与角色；每个选中的人指向人员候选响应里的真实行（调用编号、行号、主页）。姓名任务必须匹配指定姓名与公司；同名多行须明确选择。角色任务另记目标角色和所选行实际title或function原文，据真实职位说明选择理由。不得只写“第一个”。公司集团与子公司不能擅自等同。
4. 用户提供人员主页：记下该主页原值；角色任务仍记角色、职位依据和明确确认依据，不对任意主页取数。没有已确认的人员不得购买其他人的联系方式。

已查询后官网与人员选择冻结；想变更主体/角色/人员需新计划与预算。任务按全部已查询唯一人员限制总人数，不能换选择分批突破。原批次成功则复用，未查询的人可分批。中断时已发出未记结果的调用可能已扣费，不自动重试，先告诉用户；明确重试时旧费用仍保留。

部分批次成功不代表每个人都已成功：只可对响应中 error 为“本次未取到”“查询失败”或缺失响应行的人员显式重试，参数仅含其仍未成功的子集，保持原选择顺序，记下明确重试决定和依据。成功空字段和“主页不存在或未收录”不属于故障，不自动重试，不重复购买已成功人。可以沿用已授权预算，不要求每次再问用户；每次仍须在预算内，未知实扣先告诉用户。无逐人响应的失败或未知调用仅允许明确重试原批次。每次实扣都记入查询记录，结果按每人最近证据更新，历史失败留在查询记录中，已恢复的失败不再造成未完成。

## 结果与交付

成品只用已取得的数据，列出公司、官网域名、姓名、职位、人员主页、邮箱与类型、电话与类型、其他候选、匹配状态、选择依据、执行状态、取得状态、未取得原因、验证状态、在职状态、资料时间、来源、费用证据。实际缺字段留空；资料时间仅抓取时间，不代表任职变更日期。没有任职核验一律标未核验；邮箱一律未验证，不用上游email_valid冒充独立可达性验证；电话类型没有依据标未知，不能直接称手机。

官网邮箱安全去重，原行映射留在evidence；is_pattern_placeholder 为真是命名格式占位，保留标注但不算真实已取得邮箱。人员响应只接收本次已选主页，漏行/缺字段保留未知；其他人的字段不能混入。候选响应留在工作目录，可供审查未选人及同名行。

普通点和联系人点分列。费用表按唯一调用计一次，人员行只关联调用证据，不能平摊或重复累加同一名单/批量调用费用。恢复、换格式、重渲染均复用保存结果。成功空、未找到官网、身份未确定、未授权、调用失败、字段缺失分别解释；未取得不证明不存在。

取得 get_render_spec 的 O2 chat/xlsx 规范，从同一数据生成聊天和Excel并逐格回读。没有可交付结果时只说明原因，不交旧文件。合成演示的任何工作表均标“合成演示、未查询真实数据”。


每行执行状态区分查询成功、查询失败、未收录和响应未返回行，未取得原因保留实际行级提示；成功查询未提供字段与部分故障不能混写。未收录不证明不存在；失败行不借用批内成功项的抓取日期。

身份候选另表展示全部已保存官网和人员候选、选择状态、选择依据、实际来源与资料时间；同名和未选择者仍可审查，不对未选人追加联系方式查询。

## 显式采购/供应链岗位范围（配套新版）

原六项请求保持原义，指定姓名仍查全部职级，不自动按岗位缩小。关键人角色是采购或供应链（任何语言、单说“采购”也算）时，在 `role_emails` 或 `role_phones` 的原输入中显式加入本版范围：

```json
  "constraints": {
    "max_contacts": 3,
    "role_query_scope": {
      "mapping_id": "procurement_supply_chain_discovery/2",
      "components": ["procurement", "supply_chain", "owner"],
      "candidate_functions": ["Purchasing", "Operations", "Leadership"],
      "person_evidence_match": "graded_query_function_and_title",
      "small_company_max_employees": 200
    }
  },
  "outputs": {"profile": "O2", "formats": ["chat", "xlsx"]}
```

原角色可写“采购”“采购负责人”“Purchasing Manager”“Compras”“Einkauf”“供应链”等；同时含其他职能（销售、运营、财务…）或“和/及/and”并列的先待确认，不猜。没有写职能的“关键人/决策人”也先待确认。

有公司名时先查企业库登记（1点），按所绑定登记行的员工数明确定规模：200人以内为小公司，再多查一页老板/负责人（Leadership）；没有员工数或认不出是哪一行时记为未知，按非小公司处理、不查老板页。预算：采购、运营两页各100联系人点，小公司另加老板页100点。

只给公司名时，计划还查官网候选（1点），再明确选一个官网：登记官网优先；登记官网与候选一致可直接用；不一致或都没有时让用户选，或明确选择不用官网改按公司名检索。选择须绑定已保存的行，不得自拟域名；之后两页人员检索都用这个官网。官网候选常混入同名别家或同品牌其他国家站，不能直接取第一条。

人员证据分三档并逐人展示：采购页且职位含采购用词、运营页且职位含供应链用词、小公司老板页上的老板/创始人/总经理为“强”；采购页但职位没有采购用词为“中”，上游职能分类可能有误，只列入名单、不取联系方式；运营页仅含采购用词为“弱”，只作备选。职位用词按多语言词表认（compras、comprador、categoría、einkauf、achats、acquisti、inkoop、zakupy、achiziții、buyer、category manager 等），前任、否定、应付账款（purchase ledger）、人才招聘不算。公司名忽略大小写、重音、法律后缀、连接词（de、do、von、van 等）和国家名后须与冻结公司名一致；整页都不是本公司时说明官网可能不是本公司并停止，不硬选。

旧版范围（mapping_id 为 `/1`、只接受“采购/供应链负责人”这类联合别名）仍可用于在途任务，规则如下。保留原角色全文，先明确确认两类是非穷尽的候选发现范围；分别各查询一页20人，单次只传一个职能。Operations不等于供应链，过滤回显不是人员岗位事实。最多3位由实际原职位及公司关联明确选择，逐项展示原文命中片段和字面支持的采购/供应链组件；公司别名、前任/否定、歧义或两源同主页冲突无法消解则未知不选。只给域名、公司字段非空不构成个人雇主确认；在职、法律雇佣和采购权保持未核实。Sourcing缺明确采购语境不能采纳。

两页预计200联系人点，最多3人邮箱另30、电话另90；旧130/190预算不改，重新规划另确认实际明确预算及服务端权限。两个类别结果和费用都已知后可明确选择0人，详情记为不适用，不派伪调用或记虚构0费用；成功空/无合适岗位保持部分诊断，两类皆失败保留失败诊断。结果或实际费用未知时先告诉用户，不自动重试。明确零选择的已知失败诊断可作为聊天/Excel交付，摘要仍写失败、不冒业务成功。

按新计划记下范围、两页和全部选择依据，再取两格式规范出成品，全格回读，换格式复用已取得的数据。来源与费用按每次调用去重，两个来源的全部同主页原行都保留。
