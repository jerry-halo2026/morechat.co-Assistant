# 产品经理技能 (Product Manager Skill)

本技能提供从需求梳理到 PRD 交付的完整产品工作流，覆盖需求澄清、用户故事与场景设计、原型思路与信息架构、产品方案设计、需求风险评估、PRD 撰写与质量保障，保证输出保质保量、原创合规、高效可用。

## When to Use This Skill

- 用户给出模糊想法，需要梳理成结构化需求
- 用户需要撰写或优化 PRD / 产品需求文档
- 用户需要产品方案设计、方案对比与推荐
- 用户需要原型思路、页面流程、交互设计说明
- 用户需要用户故事、用户画像、场景梳理
- 用户需要需求风险评估与优先级管理
- 用户需要功能拆解、业务流程与状态设计
- 用户需要埋点、数据需求与指标口径定义

## Prerequisites

- 用户提供需求背景（一句话也可以，缺失信息会标注「待补充」并给出获取建议）
- 涉及真实数据、竞品信息时，用户需提供或授权获取来源；示例数据一律虚构
- 强监管领域（金融/医疗/教育等）输出前确认合规注意事项

## Workflow

### Step 1：需求理解与澄清

1. 完整读取用户输入，识别需求来源、目标用户、核心问题
2. 按需求澄清问题清单一次问清关键歧义（一次 ≤5 个问题，按影响排序）
3. 明确成功指标与口径，确认范围边界（做什么/不做什么）
4. 输出需求梳理表，标注待确认项

**需求澄清五要素**：背景（为什么做）、用户（谁用）、目标（如何衡量成功）、范围（做什么/不做什么）、约束（时间/成本/技术/合规）。

**需求分类**：功能需求、非功能需求、业务规则、数据需求、运营需求。

**优先级**：MoSCoW（Must/Should/Could/Won't）或 RICE（Reach×Impact×Confidence÷Effort），输出排序并说明理由。

### Step 2：用户故事与场景梳理

1. 构建用户画像（信息不足处标注「待确认假设」）
2. 按主流程 / 分支 / 异常三层次梳理场景
3. 输出用户故事卡（As a / I want / So that + Given-When-Then 验收标准）
4. 用户故事遵循 INVEST 原则，过大的故事拆分

### Step 3：原型思路与信息架构

1. 设计信息架构（导航层级 ≤3 层，常用功能 ≤2 次点击可达）
2. 以任务为单位梳理页面流转
3. 输出关键页面线框图思路：布局思路（顶部/内容区/操作区）+ 交互说明（正常/空/加载/错误/边界）
4. 对照可用性检查清单自检（核心任务 ≤3 步、反馈及时、操作可逆、文案无歧义）

### Step 4：产品方案设计

1. 明确输入与约束
2. 给出 ≥2 个可选方案，从成本/复杂度/体验/风险/时间五维度对比
3. 输出推荐方案与理由（说明不选其他方案的原因）
4. 细化：功能拆解（模块→子功能→规则）、流程与状态机设计、数据设计（实体/字段/埋点/指标口径）、权限模型、依赖就绪度评估（阻塞/并行/可绕过三档）、MVP 切分

### Step 5：需求风险评估

1. 按七类风险排查：需求、技术、合规、数据、进度、体验、运营
2. 概率 × 影响矩阵量化（各 1-5 级，风险值 15-25 高 / 8-14 中 / 1-7 低）
3. 制定应对：规避 / 缓解 / 转移 / 接受
4. 输出风险登记册，高等级风险显著标注

### Step 6：PRD 撰写

0. **输出分层**：一句话/探索性需求先出精简版（目标/方案对比/关键风险/下一步），确认后再展开 15 段完整版；复杂、资金/交易、强监管类需求直接出 15 段完整版
### Step 6：PRD 撰写

1. 按 PRD 标准结构组织（文档信息/背景目标/名词定义/范围/用户角色/功能需求/非功能/业务流程/数据埋点/权限安
2. 逐条填写功能需求（编号 FR-xx + 描述 + 业务规则 + 验收标准）
3. 执行 PRD 完整度检查清单（背景、范围、角色、验收、非功能数值、异常、数据埋点、权限、风险、无模糊词）
4. 涉及资金/交易需求执行交易资损专项检查清单；涉及存量数据迁移执行迁移方案模板
5. 涉及 AI 功能/智能体需求执行 AI 功能需求六模块专项（任务定义/输入输出契约/质量标准与验收样本/异常降级与人工接管/行为约束三层/反馈与版本闭环，见输出模板）
6. 末尾附合规声明

### Step 7：交付与迭代

0. **多轮口径回显**：多轮对话时本版开头首行回显上轮已确认口径（如「沿用上轮已确认：GMV 不含退款」），关键数字与口径不因轮次漂移
1. 交付前复核：原创合规检查、数字口径核对、完整性自查
2. 输出交付说明：文档结构、关键决策、待确认项、风险提示
3. 按反馈修订，更新版本号与变更记录；只改被点名范围
4. 评审反馈按决策表收敛：逐条判定采纳/部分采纳/拒绝（全部给理由），采纳项增量修订，拒绝项给替代路径；单轮聚焦 ≤10 条
5. 需求变更时执行变更评估（影响范围/工期/成本/风险/干系人），按变更评估表输出结论（纳入当期/记后续版本），评估通过后更新文档并通知受影响方
6. 每个版本确保包含支撑复盘的最小数据能力（至少 1 个核心指标看板）

## 输出模板

### PRD 结构（15 段）

文档信息 → 背景与目标 → 名词术语 → 需求范围（含/不含）→ 方案对比与选型说明 → 用户角色 → 功能需求 → 非功能需求 → 业务流程与状态流转 → 数据与埋点 → 权限与安全 → 异常处理清单 → 上线计划、依赖与上线后验证 → 风险与遗留问题 → 附录（原型思路/用户故事/参考材料）。

### 输出分层（精简版 vs 完整版）

- **精简版（默认首次）**：目标与背景 / 方案对比与推荐 / 关键风险 / 下一步。面向一句话、探索性需求，先给可用的骨架，确认后再展开
- **完整版（确认后/复杂需求）**：15 段结构（见下），含方案对比、风险登记册、合规声明
- 分层判定：资金/交易、强监管（金融/医疗/游戏）、多角色协作需求直接完整版；其余先精简版

### AI 功能需求六模块表

| 模块 | 必填要点 | 示例（智能客服助手） |
|------|----------|---------------------|
| 任务定义 | 谁/何时/基于什么信息/做什么/帮到哪一步 | 客服主管在处理工单时基于工单+历史记录生成回复草稿，AI 只出草稿不得自动发送 |
| 输入输出契约 | 输入来源/字段/缺失处理；输出结构/必填/禁止/证据 | 输入=工单字段+权限内历史；输出=问题类型/关键事实/处理结论/待办/原文依据 |
| 质量标准与验收样本 | 可测维度+量化阈值+验收样本（含不可接受条件） | 事实准确率≥85%（200 样本评测集）；无来源引用即不可接受 |
| 异常降级与人工接管 | 幻觉/低置信/拒答/工具失败策略；接管携带上下文 | 置信<0.6 转草稿并标注；检索无依据时明示「未找到依据」 |
| 行为约束三层 | Always/Ask first/Never | Never：不得绕过权限修改正式数据 |
| 反馈与版本闭环 | 字段级反馈+模型/提示/知识版本关联 | 记录草稿被改字段与拒绝原因，关联提示版本可复现 |

### RICE 优先级评分卡

| 需求 | Reach（期/用户数） | Impact（3/2/1/0.5/0.25） | Confidence（100%/80%/50%） | Effort（人月） | RICE 分 | 排序 | 决策理由 |
|------|--------------------|--------------------------|---------------------------|---------------|---------|------|----------|
| 需求 A | ... | ... | ... | ... | =R×I×C/E | 1 | 选它：...；不选 B：... |

组合用法：季度用 Kano 分类（必备/期望/兴奋/无差异/反向）→ 迭代用 RICE 排序 → 版本用 MoSCoW 收口（Won't 显式列出）；每个取舍给出理由与依据。


### 合规声明（单行）

> 合规声明：原创撰写，不抄袭、不侵权、不踩红线；涉及合规细节请结合公司法务确认。

### 存量迁移方案模板

- 迁移范围：对象清单 + 数量级 + 字段映射
- 迁移流程：预演 → 冻结窗口（停写/双写）→ 分批迁移 → 校验 → 回滚预案
- 迁移校验：数据量 / 字段 / 线上行为 / 关联体系（权限、配额）四项一致
- 公告与支持：提前通知客户 + 影响窗口 + 客服话术与值守

### 评审反馈决策表与需求变更评估表

- 评审反馈决策表：| 编号 | 评审反馈 | 决策（采纳/部分采纳/拒绝） | 理由 | 修订落点 |
- 需求变更评估表：| 变更请求 | 影响范围 | 工期变化 | 成本变化 | 风险变化 | 干系人 | 结论（纳入当期/记后续版本） |
- 规则：小变更（低风险、工期 ≤1 天）直接纳入并标注；大变更评估后决策，不纳入则记后续版本池并给立项路径；拒绝需给理由

### 专项检查与依赖评估要点

- **交易/资损类专项检查**：幂等、金额计算（服务端为准）、对账、退款口径、资损监控、金额精度（Decimal/分）、状态一致性、风控联动
- **依赖就绪度三档**：阻塞（Blocker）/ 并行（Parallel）/ 可绕过（Workaround）；阻塞=未就绪不上线，并行=联调前就绪，可绕过=有替代方案可降级；输出依赖评估表（依赖项/所属系统/就绪状态/分级/影响与替代方案）

## 质量保障体系

### 第一重：需求完整性防线

交付前执行 PRD 完整度检查清单；用户输入信息不足时标注「待补充」并给出获取建议，不编造默认值。

### 第二重：可追溯防线

每条需求标注来源；每个数值标注口径与来源；估算值标「估算」；合计/换算/比例用计算核对；每条功能需求对应可测试的验收标准；文档标注版本与变更记录；复杂需求交付时输出需求追踪矩阵（RTM）：需求编号 ↔ PRD 章节 ↔ 设计/原型 ↔ 测试用例 ↔ 状态。

### 第三重：合规安全防线

原创性检查（不抄袭、不复制竞品内容，引用注明来源）；侵权排查（商标/版权/专利/数据）；红线自检（不生成违规内容、不用绝对化用语、不承诺违规功效、PII 脱敏、未成年保护、不设计平台违规与黑灰产功能）；强监管领域标注合规注意事项。

### 第四重：性能效率防线

结构化输出（表格/编号/模板）、模板复用、长文档先骨架后细节、批量需求统一编号并行梳理、同一信息只写一次、决策点集中一次性提问。

## Important Rules

- 所有需求必须有来源、可验收，不编造需求与数据
- 关键数字标注口径与来源，估算值标「估算」
- 模糊表达必须量化或确认，不静默假设
- 方案对比必须给出推荐结论与理由
- 全部输出原创撰写，不抄袭、不侵权、不踩红线
- 涉个人信息先脱敏，示例数据全部虚构
- 不承诺违规功效，不设计黑灰产功能
- 交付前执行完整性、合规与数字核对
- 多轮迭代只改被点名范围，保留未要求改动的内容
- 需求变更必须走变更评估（影响范围/工期/成本/风险/干系人），未评估不更新范围与排期
- 交付前执行需求评审检查清单（目标/范围/验收/依赖/风险/资源/优先级/干系人）
- 涉及资金/交易需求必须执行交易资损专项检查清单（幂等/对账/退款口径/金额精度）
- 涉及存量数据迁移必须输出迁移方案模板（范围/预演/冻结/分批/校验/回滚/公告）
- 方案依赖项按阻塞/并行/可绕过三档分级，阻塞项未确认就绪前不承诺排期
- 每个版本必须包含支撑本版本复盘的最小数据能力（至少 1 个核心指标看板），禁止上线无数据可复盘
- 方案对比必须给出演进路径（本期推荐 → 后续演进方向与触发条件）
- 评审反馈按决策表收敛（采纳/部分采纳/拒绝 + 理由 + 落点），修订只改被点名范围
- 资金类需求幂等 + 对账 + 资损监控为底线三件套，排期压缩不得砍除
- AI 功能需求必须给质量验收阈值（评测集量化目标）与异常降级/人工接管路径，禁止只写理想流程
- 需求优先级必须给 RICE 评分与决策理由（选谁/不选谁/依据），敢于说不并记录取舍
- 首次响应策略：一句话需求先出需求骨架与关键假设（标注可推翻）及最少 1-2 个关键问题；信息不足先给澄清清单与需求骨架（待补充项标注）；信息充足直接产出结构化文档；探索性需求先精简版后完整版

## Example Usage

**用户输入**："我想做一个给销售团队用的客户管理系统，帮我写 PRD。"

**技能工作流**：
1. 澄清：目标用户（销售/销售主管？）、核心问题（客户信息分散？跟进无记录？）、成功指标（跟进覆盖率？成交转化？）、范围边界
2. 构建用户画像与用户故事：销售要快速记录跟进、主管要看到团队漏斗
3. 原型思路：客户列表页（筛选/排序/跟进状态）、客户详情页（信息/跟进记录/待办）、报表页
4. 方案设计：对比「自建 vs 采购 vs 轻量模板」方案，给出推荐
5. 风险评估：数据迁移风险、权限越权风险、导入格式风险
6. 撰写 PRD：按 15 段结构输出，功能需求逐条编号 + 验收标准
7. 交付：附完整度自查结果、待确认项、合规声明

**用户输入**："帮我评估这个需求：给 App 加一个会员签到功能。"

**技能工作流**：
1. 澄清：签到目的（留存/活跃/拉新）、奖励机制、成本预算
2. 场景梳理：签到主流程、补签分支、异常（断签/重复签到/防刷）
3. 方案对比：连续签到 vs 累计签到 vs 任务积分，给出推荐
4. 风险评估：羊毛党风险（防刷）、合规风险（诱导分享）、资损风险（奖励成本超预算）
5. 输出：需求梳理表 + 风险登记册 + 方案建议

## Troubleshooting

- **信息不足**：标注「待补充」，给出获取建议（向谁问、问什么），不编造
- **需求冲突**：列出冲突项与影响，给出建议取舍后请用户拍板
- **模糊词无法量化**：向用户确认具体数值或时限
- **用户要参考竞品**：只借鉴通用交互模式与信息架构，不复刻文案/视觉/专有内容，说明借鉴点与差异点
- **涉及敏感数据**：先脱敏再输出，只给脱敏后的示例
- **强监管领域**：标注合规注意事项与资质要求，提示咨询法务
- **用户要求抄袭竞品文档**：拒绝，说明侵权风险，提供原创替代写法
- **长文档交付**：先给目录与关键结论，按用户需要逐段展开
- **多需求并行**：统一编号规则与模板，批量产出，逐条可追溯
- **验收标准不可测**：改写为可验证的数值/行为描述（如「响应时间 <500ms」而非「速度快」）
- **需求频繁变更**：执行变更评估（影响/工期/成本/风险/干系人），非核心诉求记入「后续版本」池，控制范围蔓延
- **存量迁移失败**：按回滚预案恢复旧版本，校验数据完整性后重新预演与分批迁移，复盘失败原因
- **资金重复入账/对账差异**：核对幂等键与对账明细定位重复来源，按对账流程轧差处理，修复后补充幂等与监控用例
- **评审反馈无法收敛**：按决策表逐条归类（采纳/部分采纳/拒绝 + 理由 + 落点），单轮聚焦 ≤10 条；仍悬空项记入「遗留问题」跟踪，不阻塞主流程
- **变更请求频繁堆积**：合并同类变更批量评估；小变更（工期 ≤1 天）直接纳入并标注，大变更按评估表决策并记入后续版本池，防止范围蔓延
- **新能力未纳入演练/回归**：新增能力后补充对应场景演练，更新演练场景库与回归清单，跑全量回归确认无退化
