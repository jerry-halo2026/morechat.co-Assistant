# 运维监控体系（ops-monitoring）

> 适用角色：运维守护师（ops-sre）
> 用途：保障系统上线后稳定、安全、可观测、成本可控。上游输入：技术研发方案（部署形态与基线）、上线发布方案（发布窗口与回滚衔接）。

---

## 一、监控体系（三层指标）

监控必须三层齐备，**只有资源层监控的方案视为不合格**：

### 1.1 可用性层（服务死没死）

| 指标 | 采集方式 | 告警建议 |
|------|----------|----------|
| 服务存活 | 拨测/心跳探针（30~60s 间隔） | 连续 2 次失败即告警 |
| HTTP 可用率 | 5xx 占比、网关错误率 | 5xx 比例 >1% 持续 5 分钟 |
| 证书有效期 | HTTPS 证书监控 | 到期前 30/7/1 天分级提醒 |
| 域名/备案状态 | 定期核验 | 异常即告警 |

### 1.2 性能层（服务卡不卡）

| 指标 | 采集方式 | 告警建议 |
|------|----------|----------|
| 接口响应 | APM/网关日志（P50/P95/P99） | P95 > 基线 2 倍持续 10 分钟 |
| 慢查询 | 数据库慢日志（>200ms） | 慢查询数突增告警 |
| 队列积压 | MQ/任务队列深度 | 积压超阈值告警 |
| 资源水位 | CPU/内存/磁盘/连接数 | CPU>80% 持续 10 分钟、磁盘>85% |

### 1.3 业务层（生意好不好——必须监控）

| 指标 | 说明 |
|------|------|
| 核心业务量 | 订单量/预约量/发帖量，按小时环比（同比跌幅 >30% 告警，可能是静默故障） |
| 支付成功率 | 支付成功/发起支付，<95% 立即告警（涉及资金，等同 P0） |
| 关键转化漏斗 | 注册→激活→下单各环节转化率异常波动 |
| 第三方依赖状态 | 短信/推送/存储/地图等成功率的突降 |

**为什么业务层必须监控**：资源层一切正常但支付回调静默失败、短信通道欠费停摆，是真实事故里最常见的"无告警故障"。

## 二、告警分级

每条告警必须明确：触发阈值、持续时间、通知渠道、响应要求。"收到告警后人工排查"式的空动作告警不允许出现。

| 级别 | 定义 | 通知渠道 | 响应要求 |
|------|------|----------|----------|
| P0 | 服务不可用、资金链路故障、数据丢失风险 | 电话 + 短信（群呼轮询直至有人认领） | 15 分钟内响应，立即启动应急 |
| P1 | 核心功能降级、性能显著劣化、错误率超阈 | IM 群（工作时段）/ 短信（夜间） | 工作时间 30 分钟内响应；夜间次晨优先处理 |
| P2 | 资源水位偏高、证书临期、慢查询增多 | 邮件 / 日报汇总 | 当日或次日工作窗口处理 |

告警治理纪律：
1. **每条告警必须可执行**：告警文案里写清"哪个服务、什么指标、当前值、建议动作"；
2. **防告警风暴**：同类告警聚合收敛，抑制级联告警（数据库挂了不再重复告警每个依赖它的接口）；
3. **每月告警复盘**：误报率 >30% 的告警规则必须调优，"狼来了"的告警体系等于没有。

## 三、故障应急流程（发现 → 定位 → 恢复 → 复盘）

### 3.1 发现
监控告警 / 用户反馈 / 巡检发现，任一来源进入同一处理通道（IM 值班群 + 故障单）。

### 3.2 定位（5 分钟内给出初步判断）
1. 明确影响面：哪些用户、哪些功能、是否涉及资金；
2. 三连问：最近有没有变更（发布/配置/证书）？→ 依赖服务是否正常？→ 资源是否异常？
3. 先止血后查因：可确认是变更引起的，直接回滚（衔接发布方案的回滚预案），不在故障高峰期排查根因。

### 3.3 恢复（按预案执行）

| 故障类型 | 预案要点 |
|----------|----------|
| 服务宕机 | 重启/切换备用实例；无备实例则扩容顶住 |
| 数据库故障 | 主从切换；误删数据走备份恢复（见 3.4 前置演练） |
| 缓存雪崩 | 熔断降级非核心接口；限流保护数据库；缓存预热 |
| 流量洪峰 | 限流 + 队列削峰；静态化兜底 |
| 第三方故障 | 切换备用供应商；降级为人工/离线流程 |
| 证书/域名过期 | 紧急续期替换；对外公告影响窗口 |

### 3.4 复盘（48 小时内，不追责、追流程）
复盘报告四要素：时间线（发现/响应/恢复各时点）、根因（直接原因 + 深层原因）、影响面（用户量/时长/资金）、改进项（每项有责任人与截止时间）。改进项进入需求池跟踪，同类事故不得二次发生。

### 3.5 值班机制
小团队至少明确"第一响应人 + 备份人"及联系方式；P0 预案打印或文档置顶，故障时不需要现想。

## 四、备份策略

**没有验证过可恢复的备份等于没有备份**：

| 对象 | 策略 | 保留 |
|------|------|------|
| 数据库 | 每日全量自动备份 + binlog 增量 | 全量 ≥7 天，重要数据 ≥30 天 |
| 对象存储 | 版本控制或定期同步异地 | 与主数据一致 |
| 配置与密钥 | 配置仓库 + KMS 托管 | 每次变更留版本 |
| 代码 | 远程仓库（含 tag 与制品） | 永久 |

恢复演练：每季度至少 1 次从备份拉起恢复演练，记录 RTO（恢复耗时目标，如 ≤2 小时）与 RPO（数据丢失窗口，如 ≤5 分钟）；演练结果写入运维报告。

## 五、成本优化

### 5.1 资源弹性
- 流量波动明显的业务配置弹性伸缩（上下限写死，防失控）；
- 定时任务型负载（夜间跑批）用抢占式/闲时资源；
- 静态资源全量走 CDN，回源带宽是成本大头。

### 5.2 闲置回收
- 每月盘点：无流量的测试环境、过期快照、闲置 IP/负载均衡、废弃的第三方套餐；
- 测试/预发环境非工作时段定时关机（可省 60%+ 环境成本）。

### 5.3 预算护栏
- 月度成本预算表（各项资源 × 单价 × 预估用量）；
- 云账单阈值告警（如达预算 80% 提醒、100% 复盘）；
- 按量付费项（短信/CDN/音视频）单独设用量告警，防刷量与配置失误导致费用失控。

## 六、SLA 参考

对外承诺（或对内目标）参考值，按业务重要性选取，**承诺值必须低于实际能力**：

| 级别 | 可用性 | 月停机预算 | 适用 |
|------|--------|------------|------|
| 基础 | 99.0% | ≈7.2 小时 | 内部工具、验证期产品 |
| 标准 | 99.5% | ≈3.6 小时 | 一般 To C 业务（MVP 常选） |
| 高 | 99.9% | ≈43 分钟 | 支付、交易等资金相关链路 |

SLA 配套：明确"不可用"的统计口径（用户侧错误率而非服务器进程存活）、赔付或补偿条款（如涉及）、达标度量方式（第三方拨测数据）。

## 七、运维方案输出模板

[运维保障方案] 按此结构输出，缺章节视为未完成：

1. **部署架构**：资源清单（实例规格/数量/费用）+ 拓扑 + 环境划分
2. **监控体系**：三层指标清单（采集方式 + 存储位置 + 看板入口）
3. **告警规则表**：每条含级别/阈值/持续时间/通知渠道/响应动作
4. **应急预案**：按第三章故障类型逐项给出恢复步骤与责任人
5. **备份与演练**：策略表 + RTO/RPO 目标 + 演练计划
6. **安全加固**：基线核对（对应 tech-stack-architecture.md 安全清单）
7. **成本方案**：预算表 + 护栏告警 + 优化项
8. **SLA**：承诺值 + 统计口径 + 度量方式

## 八、日志与可观测性规范

1. **日志三分类**：
   - 访问日志（网关层：来源/路径/状态码/耗时）；
   - 应用日志（业务事件：关键动作用 INFO，可预期异常用 WARN，需人处理用 ERROR）；
   - 审计日志（登录、支付、权限变更、数据导出，留存 ≥6 个月）。
2. **结构化输出**：JSON 格式统一字段（时间戳/级别/服务/trace_id/消息），禁止纯文本自说自话；
3. **trace_id 贯穿**：一次请求跨服务共享 trace_id，排障时一查到底，不用跨机器对时间猜；
4. **脱敏**：日志禁止输出手机号全文、身份证、密码、完整卡号；
5. **保留周期**：应用日志 ≥14 天（可检索），归档 ≥90 天；磁盘水位与保留策略联动，防止日志写满磁盘触发新故障。

## 九、安全运维与演练日历

| 周期 | 动作 |
|------|------|
| 每日 | 备份任务成功核验；告警静默检查 |
| 每周 | 补丁与漏洞通告核对；异常登录/暴力破解日志抽查 |
| 每月 | 资源与账单盘点（闲置回收）；告警规则调优；证书/域名有效期核对 |
| 每季度 | 备份恢复演练（验证 RTO/RPO）；应急预案桌面推演（P0 场景走一遍） |
| 每半年 | 权限盘点（离职/转岗账号回收）；密钥轮换 |

## 十、与其他阶段的衔接

- **输入**：接收发布方案（release-deployment.md）的部署形态、回滚预案与 72 小时观察结论；
- **输出**：稳定性数据（可用率/故障记录）反哺研发方案的架构演进（tech-stack-architecture.md）；
- **协作**：向运营方案（growth-retention.md）提供系统容量数据——大促/裂变活动前必须做容量评估，活动量级超出基线时提前扩容。

## 十一、MVP 阶段监控最小集（低成本起步）

小团队/低预算起步时，按此最小集建设，随业务增长逐项升级：

| 项 | 最小实现 | 成本 |
|----|----------|------|
| 可用性拨测 | 云监控/免费拨测服务，1 分钟间隔探活 | 免费~低 |
| 错误与日志 | 云日志服务或轻量自建（结构化 + 检索） | 低 |
| 告警通知 | 短信/IM 机器人，P0 电话用云电话API | 低 |
| 业务指标 | 定时任务查询数据库生成日报（订单/注册/支付成功率） | 几乎为零 |
| 证书监控 | 到期提醒脚本或第三方免费监控 | 免费 |
| 备份 | 云数据库自动备份开启（默认能力，务必核验已开启） | 极低 |

升级触发条件：并发或收入上量、出现第一起 P0 故障、团队人数 >5 ——任一发生即按第一~五章完整体系升级，不建议跳级建设。
