# 技术选型与架构（tech-stack-architecture）

> 适用角色：全栈研发师（fullstack-engineer）
> 用途：产出与产品规模、团队能力匹配的技术方案。上游输入：`platform-selection.md` 的端组合与 `product-design.md` 的 PRD。

---

## 一、技术选型对比表

### 1.1 前端框架（Web / 后台）

| 方案 | 优势 | 劣势 | 适用 |
|------|------|------|------|
| Vue 3 + Element Plus / Naive UI | 上手快、中文生态好、后台模板丰富 | 超复杂前端状态管理一般 | 后台管理系统、常规 Web 应用（国内首选） |
| React + Ant Design | 生态最大、组件全、人才多 | 心智负担略高 | 团队熟 React、复杂交互应用 |
| Next.js / Nuxt（SSR） | SEO 友好、首屏快 | 部署运维复杂度上升 | 内容站、官网、需要搜索流量的产品 |
| 纯静态站（Hugo/Vite + CDN） | 成本极低、速度快 | 无后端交互 | 官网、落地页、文档站 |

### 1.2 移动端跨端方案

| 方案 | 优势 | 劣势 | 适用 |
|------|------|------|------|
| iOS 原生 Swift / Android 原生 Kotlin | 性能与体验上限最高、系统能力无障碍 | 双端两套成本 | 重体验 App、预算充足 |
| Flutter | 双端高一致性、性能好、生态成熟 | 包体大、平台特性需插件、鸿蒙需附加路线 | 中大型跨端 App |
| React Native | 前端团队复用、热更新成熟 | 性能敏感页需原生协助 | Web 团队做 App |
| uni-app | 一套代码覆盖 App+小程序、国内生态 | 体验上限较低 | 预算紧 + 多端（含小程序） |

### 1.3 后端语言与框架

| 方案 | 优势 | 劣势 | 适用 |
|------|------|------|------|
| Node.js（NestJS/Express） | 与前端同构、全栈一人可 cover | CPU 密集型弱 | 中小项目、实时类应用 |
| Python（FastAPI/Django） | 开发快、AI 生态强 | 高并发需额外架构 | 快速 MVP、含 AI 能力 |
| Java（Spring Boot） | 生态稳、人才多、企业级 | 重量级、启动慢 | 团队熟 Java、业务复杂的中大型 |
| Go（Gin/GoFrame） | 并发强、部署简单（单二进制） | 生态较年轻、泛型表达力 | 高并发服务、工具型后端 |
| PHP（Laravel） | 部署廉价、传统建站生态 | 高并发弱、趋势下行 | 用户只会 PHP 的存量场景 |

### 1.4 数据库

| 方案 | 适用 | 注意 |
|------|------|------|
| MySQL | 90% 业务系统的默认选择：订单、用户、内容 | 电商/金融注意事务与索引设计 |
| PostgreSQL | 复杂查询、JSONB、地理数据（PostGIS） | 功能更强，国内云托管稍少 |
| SQLite | 单机工具、桌面软件、极小流量 | 并发写弱，禁止用于多用户 Web 生产 |
| Redis | 缓存、会话、排行榜、分布式锁 | 必须配持久化策略，防缓存雪崩 |
| MongoDB | 文档结构多变、日志类 | 强事务业务慎用 |

**选型总原则**：先团队技能栈 → 再业务形态 → 最后才是性能榜单。选没人会维护的"先进"技术是负分。

## 二、架构模式选择

| 模式 | 适用场景 | 判据 |
|------|----------|------|
| 单体（含模板渲染） | MVP、个人/小团队、日活万级以内 | 默认起点，能单体就单体 |
| 前后端分离单体 | 有独立 H5/App 前端 + API 后端 | 多端共用一套 API 时的标准形态 |
| 微服务 | 多团队并行、模块负载差异巨大、成熟业务 | 日活数十万+ 或组织需要时才上 |

**演进路径**：单体 → 模块化单体（清晰分包）→ 按需拆分高负载模块。禁止"MVP 直接上微服务"。

### 部署拓扑基线（中小项目）

```
用户端（Web/App/小程序）
   │ HTTPS
   ▼
CDN / WAF（静态资源 + 防护）
   ▼
Nginx / 负载均衡
   ▼
应用服务（1~2 台或 Serverless / 容器）
   ▼
MySQL（主库，云托管为主） ── Redis（缓存/会话）
   │
   ├── 对象存储（图片/文件，直传+CDN）
   └── 第三方：支付 / 短信 / 推送 / 统计
```

## 三、数据模型设计要点

1. **主键**：统一用自增 ID 或分布式 ID，业务编号（订单号等）另设业务键；
2. **时间戳三件套**：`created_at`、`updated_at` 必备，重要表加软删除 `deleted_at`；
3. **状态机字段**：订单/审核类表用显式状态字段（状态枚举 + 流转规则写进 PRD）；
4. **金额**：一律整型分（或 DECIMAL），禁止浮点存钱；
5. **扩展预留**：只对已明确的方向预留（如多租户加 `tenant_id`），不为空想需求堆字段；
6. **索引**：按高频查询路径建索引（列表页筛选、登录查询），外键字段必建索引；
7. **冷热分离**：大表（日志、消息）预留归档策略，避免首年就拖慢主库。

---

## 四、API 设计规范

1. **RESTful 基线**：资源名词复数 + HTTP 动词（GET/POST/PUT/DELETE），操作类动作可用 `/orders/{id}/cancel` 子资源表达；
2. **统一响应结构**：`{ code, message, data }`，业务错误码分段定义（4xx 客户端问题、5xx 服务端问题），禁止 200 包一切；
3. **认证**：JWT 或 Session，Token 有效期 + 刷新机制；小程序/App 与 Web 共用同一套 API 网关鉴权；
4. **版本化**：`/api/v1/...`，破坏性变更升版本；
5. **分页**：列表接口强制分页（page/pageSize 或 cursor），禁止无上限全量返回；
6. **幂等**：支付、下单等写操作必须幂等（客户端生成请求 ID，服务端去重）；
7. **文档**：OpenAPI/Swagger 同步维护，联调以文档为准。

## 五、多端适配要点

### iOS（App Store）
- 审核周期与被拒高发点：隐私清单（PrivacyInfo）、隐私权限文案（相机/相册/定位必须写用途）、虚拟商品必须走 IAP（数字内容）、诱导下载/裂变文案、功能与描述不符；
- 账号体系：支持"Sign in with Apple"（若接了第三方登录）；
- 热更新受限：动态下发代码须遵守平台规则，业务配置类可走远程配置。

### 鸿蒙（HarmonyOS / ArkTS）
- ArkTS 语法基于 TS 但有约束（禁 any、限制运行时动态性），从 TS 代码迁移需适配；
- 页面路由、生命周期（UIAbility）与 Android 不同，需重新组织工程结构；
- 上架走华为应用市场（AGC），审核要点含隐私、权限、元服务规范；多端部署（手机/平板/折叠屏）注意自适应布局（断点/栅格）。

### 微信小程序
- 包体积：主包 ≤2MB、整包 ≤30MB（分阶段放开），超限用分包加载 + 静态资源走 CDN；
- 域名白名单：request/upload/download 域名必须备案且 HTTPS，提前在小程序后台配置；
- API 与审核：涉及类目资质（电商/社交/医疗）、虚拟支付限制（iOS 端小程序虚拟商品支付受限）、订阅消息频次规则；
- 兼容：基础库版本梯度、低版本机型降级策略。

### Web
- 浏览器兼容基线（Chrome/Edge/Safari 主流两版 + 移动端浏览器）、响应式断点；
- 首屏性能预算：FCP ≤2s（4G），图片走 CDN 与懒加载。

## 六、常见架构误区

1. **过度设计**：MVP 上微服务、K8s、多级缓存、读写分离——复杂度是负债，先活下来再优化；
2. **技术栈与团队错配**：招不到/不会维护的技术选型，等于给项目埋雷；
3. **忽视多端差异**："一套代码全端通用"的乐观假设——各端能力、审核、限制差异巨大，必须逐端核对；
4. **数据模型短视**：无时间戳、无软删除、状态用字符串魔法值、金额用浮点——上线后改造成本指数级上升；
5. **安全后置**：明文存密码、密钥硬编码、接口无鉴权——安全是底线工程，必须在 V1.0 做对；
6. **无观测设计**：没有任何日志/埋点/错误上报，上线后等于盲飞；
7. **单点依赖无备份**：数据库无备份策略、第三方服务无降级方案——故障时无路可退。

## 七、非功能性需求基线

技术方案必须明确以下基线（写进方案，测试据此验收、运维据此建设）：

| 维度 | MVP 基线参考 | 说明 |
|------|--------------|------|
| 并发 | 支持 100~500 并发在线 | 超出需重新评估架构与成本 |
| 响应 | 核心接口 P95 ≤ 500ms；页面首屏 ≤ 2s（4G） | 弱网另测 |
| 可用性 | 月度 ≥99.5% | 对应运维方案的 SLO |
| 崩溃率 | App ≤0.1% | 上线门禁项 |
| 安全 | HTTPS 全站、密码哈希存储、接口鉴权全覆盖 | 底线要求，不可妥协 |
| 备份 | 数据库每日自动备份 + 保留 ≥7 天 | 对应运维方案 |

## 八、第三方服务选型速查

自研 vs 第三方的判定：**非业务核心能力一律第三方**。常用类目与注意项：

| 能力 | 常用选项 | 选型注意 |
|------|----------|----------|
| 支付 | 微信支付、支付宝、聚合支付 | 主体资质要求；费率与结算周期；回调必须幂等 |
| 短信 | 阿里云/腾讯云 SMS | 模板报审周期；签名规范；防刷频控 |
| 推送 | 厂商通道（华为/小米/OPPO/vivo）+ 聚合推送 | 国内安卓必须走厂商通道，自建通道到达率极低 |
| 对象存储 | OSS/COS + CDN | 客户端直传签名、防盗链、图片压缩 |
| 地图 | 高德/腾讯/百度 | 配额限制与商用授权 |
| 即时通信 | 腾讯 IM / 环信 | 自研成本极高，MVP 不建议 |
| 音视频 | 声网/腾讯 TRTC | 按用量计费，必须先做成本测算 |
| 统计 | 友盟/微信自带 + 自建埋点 | 关键指标以自建埋点兜底 |

每项写明：选定方案、申请前置项（资质/审核周期）、月成本量级、降级方案（第三方挂了怎么办）。

## 九、安全基线清单

1. **传输**：全站 HTTPS，禁用弱加密套件；
2. **存储**：密码 bcrypt/argon2 哈希；手机号/身份证等敏感字段加密存储；密钥走 KMS/环境变量，禁止硬编码进代码库；
3. **接口**：全部非公开接口鉴权；水平越权校验（资源归属校验）；敏感操作二次确认；
4. **输入**：参数校验 + ORM/参数化查询防注入；富文本白名单过滤防 XSS；
5. **风控**：验证码/频率限制防刷（注册、短信、下单、优惠券领取）；
6. **审计**：关键操作日志（登录、支付、权限变更）留存 ≥6 个月。

## 十、技术方案输出模板

[技术研发方案] 按此结构输出，缺章节视为未完成：

1. **技术选型总表**：端 × 层（前端/后端/数据库/中间件/第三方）+ 每项一句选择理由
2. **系统架构说明**：拓扑图（文字描述）+ 核心请求链路 + 部署形态
3. **模块划分**：业务模块清单 + 模块间依赖关系（禁止循环依赖）
4. **数据模型**：核心实体 ER 说明 + 关键表字段与索引设计
5. **API 清单**：核心接口列表（方法/路径/鉴权/幂等性）
6. **多端适配说明**：逐端核对第五章要点，给出规避措施
7. **非功能性承诺**：对应第七章基线的具体数值
8. **技术风险与预案**：Top3 风险 + 触发条件 + 应对措施
