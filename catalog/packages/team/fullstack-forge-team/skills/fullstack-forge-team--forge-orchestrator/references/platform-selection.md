# 平台选型决策（platform-selection）

> 适用角色：选品洞察师（product-scout）
> 用途：在需求确认后，决定"在哪些平台上做、用什么形态做"。需求梳理请先阅读 `requirement-analysis.md`。

## 一、七类平台对比矩阵

| 维度 | 网站（Web） | App（跨端） | 小程序（微信） | iOS 原生 | 鸿蒙（HarmonyOS） | 桌面软件 | 公众号 H5 |
|------|------------|-------------|----------------|----------|--------------------|----------|-----------|
| 开发成本 | 低~中 | 中 | 低~中 | 中~高 | 中（生态趋成熟） | 中~高 | 最低 |
| 获客入口 | 搜索引擎/链接直达 | 应用商店/推广 | 微信搜一搜/扫码/分享 | App Store | 华为应用市场/多端部署 | 官网下载/分发站 | 公众号粉丝 |
| 能力边界 | 受浏览器限制，无法后台常驻 | 系统能力全（推送/蓝牙/传感器） | 受微信容器限制（包体积、API 白名单） | 系统能力全+体验最佳 | 分布式软总线、跨设备协同 | 本地文件/硬件外设/离线能力强 | 弱，仅网页+JS-SDK |
| 审核周期 | 无商店审核（需 ICP 备案） | 安卓各家商店 1~7 天 | 微信审核 1~7 天 + 类目资质 | App Store 1~7 天，被拒率高发 | 华为审核 1~3 天 | 无统一商店（自分发或商店） | 无独立审核（依公众号类目） |
| 上手/留存 | 一次性访问多，靠域名/收藏 | 留存最好（图标常驻+推送） | 用完即走，靠入口与消息触达 | 留存好 | 留存好 | 使用频次低的工具型场景 | 依托公众号打开率 |
| 更新灵活性 | 秒级发版 | 商店审核+热更新限制 | 审核后即全量，包体限制 2MB~30MB（分阶段） | 审核后生效 | 审核后生效 | 自主推送更新 | 秒级 |
| 适用场景 | 官网/内容站/SaaS 后台/工具站 | 高频、重交互、需系统能力 | 轻频次、社交裂变、线下扫码 | 面向 iOS 付费用户/重体验 | 面向华为设备用户/国产化要求 | 重本地计算/外设/企业内网 | 轻量服务、内容触达、客服 |

**阅读提示**：先看"获客入口"和"能力边界"两行——获客入口决定用户从哪来，能力边界决定核心功能做不做得成。

## 二、目标用户设备习惯判断法

平台选型必须从"目标用户在什么设备上、什么状态下用"出发，而不是从技术偏好出发。

### 2.1 四步判断法

1. **画用户状态**：目标用户在什么地点、什么时间、手持什么设备产生需求？
   - 通勤碎片时间刷手机 → 移动端优先
   - 办公场景长时间操作 → 桌面/Web 优先
   - 门店/线下场景 → 扫码即用 → 小程序优先
   - 车间/仓储/户外作业 → 三防安卓机/工业平板/鸿蒙设备
2. **判使用频次**：高频（日活型）App 可装；低频（月用一两次）装 App 会被卸载，小程序/网站更合适。
3. **判人群设备构成**：中老年/下沉市场 → 微信生态接受度最高；iPhone 占比高的消费人群 → iOS 不可缺；企业客户 Windows 为主 → 桌面端/Web；政企国产化要求 → 鸿蒙优先。
4. **判关键动作**：需要推送唤醒（订单/消息）→ App 或小程序订阅消息；需要扫码/蓝牙/NFC/摄像头 AI → 小程序可覆盖大部分，重传感器用 App；需要大量本地计算/大文件处理 → 桌面软件。

### 2.2 常见误判纠正

- "老板都用 iPhone 所以只做 iOS"：先确认**目标用户**的设备构成，老板不等于用户；
- "做个 App 显得正规"：低频工具做 App 只会收获卸载率；
- "小程序什么都能做"：小程序无法常驻后台、推送能力有限、包体积受限，重功能会撞墙。

## 三、组合策略

单端经常不成立，用组合补齐"入口 + 管理侧"：

| 组合 | 典型场景 | 说明 |
|------|----------|------|
| 小程序 + 简易后台 | 线下门店预约、点单、会员 | C 端扫码即用，B 端用 Web 后台管理商品/核销 |
| 网站 + 小程序 | 内容/品牌站 + 转化入口 | 官网承接搜索流量，小程序承接复购与服务 |
| App（双端）+ 后台 | 高频服务、社区、工具 | iOS + Android 跨端开发，后台管内容与用户 |
| iOS 原生 + 后台 | 付费意愿高的 iOS 人群 | 体验与付费转化优先，Android 后补 |
| 鸿蒙 + 安卓 + iOS 三端 | 政企/国产化/华为渠道要求 | 优先考虑跨端框架降本，鸿蒙可后置跟随 |
| 桌面软件 + Web 控制台 | 设计工具、数据采集、外设控制 | 本地重活桌面做，云端协同 Web 做 |
| 公众号 H5 + 社群 | 极轻量验证期产品 | 零审核成本快速试水，跑通再加端 |

**组合决策原则**：先用最便宜的组合验证需求成立，再升级端形态；每加一个端都是长期维护成本（多端一致性、多份审核），必须有明确理由。

## 四、跨端方案判断

确定做 App 后，再决定原生还是跨端：

| 方案 | 优势 | 劣势 | 适用 |
|------|------|------|------|
| 原生（Swift/Kotlin） | 性能、系统能力、审核稳妥 | 双端两套代码，成本高 | 重体验、重系统能力、预算充足 |
| Flutter | 双端一致性好、性能接近原生、生态成熟 | 包体偏大、平台特定能力需插件 | 中大型跨端 App 主流选择 |
| React Native | 前端团队复用、热更新生态 | 复杂动画/性能敏感页需原生协助 | Web 团队扩展移动端 |
| uni-app | 一套代码多端（含小程序）、国内生态 | 复杂交互体验上限较低 | 预算有限 + 需要同时覆盖小程序和 App |

决策顺序：**预算与团队能力 → 是否需要同时上小程序 → 性能/体验要求 → 生态成熟度**。

## 五、选型决策树

```
开始
 ├─ 需求是否合法合规？
 │   └─ 否 → 终止（一票否决）
 ├─ 用户主要在什么设备上产生需求？
 │   ├─ 桌面/长时操作 → 桌面软件 或 Web 应用（要协作/远程 → Web 优先）
 │   ├─ 线下扫码/微信内传播 → 微信小程序（+ 简易后台）
 │   ├─ 移动高频 + 需推送/系统能力
 │   │   ├─ 预算充足、体验优先 → 原生双端（或 iOS 原生先行）
 │   │   ├─ 同时需要小程序 → uni-app 或 跨端 + 小程序组合
 │   │   └─ 常规 → Flutter / RN 跨端
 │   ├─ 移动低频 → 小程序 或 公众号 H5（验证期）
 │   └─ 政企/国产化要求 → 鸿蒙优先，其余端按需组合
 ├─ 是否需要 B 端管理后台？
 │   └─ 几乎总是 → Web 后台（与技术栈同构优先）
 └─ 输出：推荐端组合 + 每个端的理由 + 备选方案 + 待用户确认项
```

## 六、选型报告必含结论项

1. **推荐端组合**（唯一主推荐）：每端一句话理由；
2. **备选组合**：在什么条件变化时切换（如"若预算增加 50%，建议升级原生双端"）；
3. **各端关键风险**：审核周期、类目资质、包体积、推送限制等；
4. **与目标用户设备习惯的对应关系**：引用第二章四步判断法的结论；
5. **待用户确认项**：影响选型但尚未确认的信息（预算、主体资质、渠道资源）。

## 六、上架资质与合规速查表

| 平台/端 | 硬性前置 | 常见类目资质 | 周期参考 |
|---------|----------|--------------|----------|
| 网站（大陆服务器） | ICP 备案 | 经营性网站需 ICP 许可证 | 备案 1~3 周 |
| 微信小程序 | 微信认证 + 服务器域名备案且 HTTPS | 电商（EDI/ICP）、餐饮（食品经营许可）、医疗（行业资质）、直播（网络文化许可） | 认证 1~3 天，审核 1~7 天 |
| App Store（iOS） | Apple Developer 账号（99 美元/年） | 金融/健康类强资质，多数类目无额外 | 首审 1~7 天 |
| 安卓各商店 | 软件著作权（多数商店要求）、隐私政策链接 | 特殊类目同上 | 每家 1~7 天 |
| 华为应用市场（鸿蒙） | AGC 账号、签名证书 | 同安卓 | 1~3 天 |
| 桌面软件 | 无统一商店（自分发或第三方分发站） | Windows 驱动类需代码签名证书 | — |

**使用规则**：凡选型结论涉及上表的端，报告必须注明对应"硬性前置"是否已具备；未具备的写入待确认清单并提示周期，防止排期踩空。

## 七、成本量级参考（用于校验预算合理性）

以下为国内市场粗略量级（一人月 ≈ 20 人日），用于校验用户预算与期望是否匹配，不构成报价：

| 产物形态 | 典型工作量 | 适用 |
|----------|------------|------|
| 公众号 H5 / 落地页 | 3~10 人日 | 极简验证 |
| 展示型官网 | 5~15 人日 | 品牌/内容展示 |
| 小程序（C端 + 简易后台） | 20~50 人日 | 预约/点单/轻量电商 |
| Web 应用 + 后台 | 30~80 人日 | SaaS 工具、管理系统 |
| 跨端 App + 后台 | 60~150 人日 | 完整移动产品 |
| 原生双端 App | 100~200+ 人日 | 重体验产品 |

运行成本月度参考：云服务器（入门 100~500 元）、云数据库（50~300 元）、CDN/对象存储（按量计费，图片视频站另计）、短信（0.04~0.05 元/条）、HTTPS 证书（免费 Let's Encrypt ~ 付费 DV 数千元/年）。

**校验红线**：用户预算低于对应形态工作量下限 × 0.6 时，必须提出降配方案（砍端/砍功能/分期交付），不得硬接需求。

## 八、典型选型案例

### 案例 1：社区团购接龙工具 → 小程序 + Web 后台
用户是宝妈团长，其顾客全在微信群里接龙下单。判断：用户全在微信生态、低频轻交互、依赖群传播 → 小程序；团长需要商品与订单管理 → Web 后台。若直接做 App：获客链路断裂（顾客不会为接龙装 App）。

### 案例 2：健身房连锁 SaaS → Web 应用 + 员工端小程序
门店管理、报表、会员运营是长时桌面操作 → Web 后台；教练带课扫码签到是移动碎片场景 → 小程序。判断依据：不同角色使用状态不同，分端承接。

### 案例 3：摄影修图工具 → 桌面软件 + Web 控制台
处理大文件、依赖本地算力 → 桌面软件；账号授权与素材云同步 → Web。若做小程序：包体积与算力直接不可行。

## 九、选型反模式（出现即修正）

1. **一上来全平台**："网站 + App + 小程序 + 鸿蒙一次做齐"——未验证预算与运营承接力，改为单端先行的版本路线图；
2. **技术偏好驱动选型**：开发者说"我想用 XX 新框架练手"——端形态应由用户设备习惯与业务场景决定，团队练手诉求不是选型依据；
3. **复制竞品的端组合**：竞品可能有多年的历史包袱，其组合不等于当前最优解，回到用户与场景推导；
4. **忽略 B 端**：只规划 C 端不做运营后台，上线即"无法运营"——绝大多数业务型产品都需要最小后台；
5. **选型报告没有结论**：罗列优缺点后不给唯一推荐与理由，等于没做选型。

## 十、各端推送与触达能力对照（决定召回上限）

| 端 | 触达手段 | 频次限制 | 召回能力 |
|----|----------|----------|----------|
| App | 厂商推送通道 + 站内消息 | 平台无硬性限制（自查锁屏策略） | 强，可唤醒沉睡用户 |
| 微信小程序 | 订阅消息（一次性/长期）、服务通知 | 一次性订阅需用户逐次授权 | 中，依赖用户授权意愿 |
| 公众号 H5 | 模板消息/客服消息（48h 窗口） | 模板消息类目受限 | 中弱 |
| 网站 | 邮件、短信 | 无平台限制，注意反垃圾与合规 | 弱，依赖用户主动回访 |
| 桌面软件 | 应用内通知 + 邮件 | 无 | 中 |

**使用规则**：运营方案（growth-retention.md）的召回设计必须以本表的触达能力为边界；选型报告中涉及强召回业务（如提醒类、社交类）的产品，应据此提升 App/小程序的权重。

## 十一、选型结论与下游交接

选型不是终点，结论将作为三个下游的输入：
1. **产品主理人**：端组合决定 PRD 的多端体验规划与版本路线图顺序；
2. **全栈研发师**：端组合决定技术选型范围（跨端方案、各端适配项）；
3. **上线发布师**：端组合决定发布通道清单与资质准备（release-deployment.md）。
因此选型报告中的"推荐端组合"必须精确到每个端的形态（如"微信小程序（C端）+ Web 后台（B端）"），不能停留在"做个移动端"的粒度。
